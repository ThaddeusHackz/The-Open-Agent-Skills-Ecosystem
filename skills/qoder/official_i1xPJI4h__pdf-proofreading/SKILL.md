# PDF電験三種技術書 校正スキル

日本語の電気工学書（特に電験三種関連）の **1章分PDF（最大40ページ前後）** を校正するためのワークフローをガイドする。
**重要な前提**: 利用者は電気工学の専門家だがプログラミング初心者である。各ステップの冒頭で現在地を伝え、必ず確認を取りながら進めること。

---

## 入力の渡し方（前提）

**ユーザーは校正対象のPDFをチャットに直接添付する**（ファイルパスでの引き渡しではない）。

そのため、Codexは：
- 添付PDFの**本文テキスト**を直接読み取る（`pdftotext` 不要）
- 添付PDFの**各ページ画像**を直接視覚確認する（`pdftoppm` 不要、`pages/` フォルダ生成も不要）

外部ツール（Poppler / pdftotext / pdftoppm）に依存せず、**Codexが受け取った添付PDFそのものを「原本」として扱う**。これが本スキルの基本運用。

> 補足：もしファイルパスで渡された場合（添付できない大容量PDF など）は、エラー扱いにせず「PDFをチャットに添付して再送してください」と案内する。

---

## 運用ポリシー（必ず守ること）

1. **元PDFは絶対に編集しない**。修正はすべて別ファイル（`corrections_sectionNN.md`）に「提案リスト」として出力する。
2. **PDFを1回渡したら `REPORT.md` が出力されるまで Step 1〜3 をすべて自動で進める**。ユーザー承認は求めず、途中で止めない。分割案・GLOSSARY・STYLE も**報告のみ**で承認待ちしない。各ステップ冒頭で「今どのステップか」を一文で宣言して進行する（例：「◆ Step 1/3: 節分割を実行します」）。**中断する唯一の条件は致命的エラー**（添付PDFが画像ベース（スキャン）で本文テキストが取れない／40ページを大幅超過）に限る。
3. **コマンド実行前に、何をするかを日本語で一文添える**。質問や確認は付けず、実行に進む。
4. **「原本の誤記」か「PDF抽出時の崩れ」かを必ず区別する**。判断がつかない場合は「要確認」として両方の可能性を併記する。
   - **特例：単位の `n` ⇔ `μ`（マイクロ／ナノ）の不一致は、原本誤記と即断せず、必ず `[要確認：原本の誤記 or 抽出ミス]` に分類する**。これはPDF抽出/OCRの仕様上、`nF` ⇔ `μF`、`nC` ⇔ `μC` などが相互に化けることが極めて多いため。たとえ「計算上 μF でないと答えが合わない」「問題文と解答の単位がずれている」場合でも、原本側のフォントの目視確認が必要なため判断保留にする。詳細は `ocr_quirks.md` セクション 1-a を参照。
5. **図・表・グラフ・回路図に関する指摘を行う前に、必ず添付PDFの該当ページの画像を視覚確認する**。本文抽出テキストの断片的な数値や文字列だけを根拠に図の内容を推測してはならない。視覚確認せずに出す指摘は禁止。視覚確認しても判断がつかない場合は **[要確認：図の原本目視確認]** として指摘する。
6. **ユーザーが明示的に「止めて」「確認してから進めて」と指示した場合のみ**、該当ステップで停止する。デフォルトは全自動。

---

## 成果物の配置場所

成果物は `output/<章名>/` 以下に章ごとに分離して生成する。**配置先のベースパスは以下の優先順で自動決定する**：

1. **既存の同シリーズ章の出力ディレクトリがあれば、その隣に並べる**（最優先）。具体的には、IDE-opened ファイルや直近の作業履歴から `…/Codex出力/<同シリーズの別章>/output/REPORT.md` のようなパスが取得できる場合、その親ディレクトリ（`…/Codex出力/`）の直下に `<章名>/output/` を置く
2. **ユーザーが過去の会話で出力先を明示している場合**はそれを尊重
3. **どちらも該当しない場合**のみ、プロジェクトルート直下の `output/<章名>/` を使う

判断材料が複数あって迷ったら、Step 0 の宣言時に推定パスを一文で報告して進める（承認は求めない）。例：「出力先は既存の `…/Codex出力/アカデミア_理論_念校_3章/output/` を使用します」。

`<章名>` はユーザーがPDFを添付したときの章タイトル・章番号から自動命名する（例：「4章」「第4章_交流回路」「アカデミア_理論_念校_4章」など。同シリーズの既存章があればその命名規則を踏襲する）。

```
<出力ベース>/
└── <章名>/
    └── output/                                  ← 既存章の運用がこの形なら踏襲、なければ <章名>/ 直下も可
        ├── sections/
        │   ├── section01.txt                    ← 5ページ前後で分割した節（添付PDFから本文を整理して書き出し）
        │   ├── section02.txt
        │   └── ...
        ├── GLOSSARY.md                          ← Step 2 の用語集
        ├── STYLE.md                             ← Step 2 の表記ルール
        ├── corrections/
        │   ├── corrections_section01.md         ← Step 3 の節ごと修正提案
        │   ├── corrections_section02.md
        │   └── ...
        ├── REPORT.md                            ← Step 3 完了時の全節サマリレポート（1ファイル集約版）
        └── REPORT_merged.md                     ← Codex等の別レポートが見つかった場合のみ生成（Step 4）
```

> 注：`pages/` フォルダはチャット添付運用では作らない（添付PDFを直接視覚確認に使う）。
> 注：生テキスト（`<input>.txt`）も外部ツール抽出を行わないため作らない。代わりに `sections/sectionNN.txt` に節ごとの本文を整理して書き出す。
> 注：既存の同シリーズ章のディレクトリ構造（`<章名>/output/` か `<章名>/` 直下か）はそのまま踏襲する。混在を避ける。

---

## Step 0: 全体フローの宣言（承認待ちしない）

PDFを受け取ったら、利用者に**一度だけ**以下を伝え、**そのまま Step 1 に進む**（承認は求めない）：

> これから1章分のPDFを校正します。Step 1（節分割）→ Step 2（GLOSSARY/STYLE 生成）→ Step 3（節ごとの校正 ＋ REPORT.md 集約）まで自動で進め、最終成果物の REPORT.md を出力します。途中で止めてほしい場合はお声がけください。

続けて、`.Codex/skills/pdf-proofreading/` 配下にある以下の補助ファイルを `Read` で読み込んで、以降の作業に利用する：

- `ocr_quirks.md` — PDF抽出時に崩れやすい文字・記号の対応表（添付PDFの本文テキスト読み取りでも一部の記号は崩れて見えるため引き続き有用）
- `correction_template.md` — 修正提案リストの出力フォーマット
- `glossary_template.md` — `GLOSSARY.md` の雛形（電験三種向け記入例あり）
- `style_template.md` — `STYLE.md` の雛形（電験三種向け記入例あり）

## ◆ Step 1/3: 節分割

### 1-1. 事前チェック
- 添付PDFが本文テキストを含んでいるか確認（添付PDFを直接読んで、本文テキストが取得できれば OK）
- 取得できない／極端に短い場合 → 「このPDFは画像ベース（スキャン）の可能性があります。OCRをかけたPDFを再送してください」と伝えて中断
- ページ数が 50ページを大きく超える場合 → 警告を出し、章単位で分割した上で再添付するよう依頼

### 1-2. 出力先フォルダの準備
- 章名（`<章名>`）をユーザーの添付ファイル名や章タイトルから推定（例：「アカデミア_理論_念校pdf（4章）.pdf」→ `4章`）
- 既存の `output/<章名>/` がある場合は上書き確認するか、別名（`4章_v2/` など）を提案
- `output/<章名>/sections/` と `output/<章名>/corrections/` を `mkdir -p` で作成
- **`mkdir` が permission/sandbox エラーで失敗した場合の代替**：`Write` ツールで `<出力先>/sections/.gitkeep` と `<出力先>/corrections/.gitkeep`（中身は空文字列）を書き込む。`Write` は親ディレクトリを自動作成するため、この方法でフォルダ生成が完了する。`mkdir` 失敗で作業を止めない

### 1-3. 節構造の検出
- 添付PDFの本文を通読し、以下を手掛かりに節・小見出しを推定：
  - 見出しの書式（「4-1」「4-2」「1.1」「1.2」など番号付き節）
  - 太字・中央寄せの小見出し
  - 明確な区切りがない場合は、本文の話題の切れ目を目安にする
- 1ファイルあたり **5ページ前後** を目安に分割案を作る
- **8節前後**（40ページ÷5ページ）を想定。実際の章の節数に合わせる

### 1-4. 分割案の提示と即時実行（承認待ちしない）
- 以下の形で分割案を**報告し、そのまま分割実行に進む**：
  ```
  【分割案】（4章＝約30ページを5節に分割）
  section01.txt … 「4-1 交流のキホン」（本誌 p.242〜253）
  section02.txt … 「4-2 交流回路のキホン」（本誌 p.254〜273）
  ...
  ```
- ユーザーからの承認は求めない。**報告直後に `sections/sectionNN.txt` を書き出す**。
- 各 `sectionNN.txt` には添付PDFの本文を整理して転記する（節の見出し・本文・公式枠・問題と解説など）。
- 分割が明らかに不自然と判断した場合（見出しが一切検出できない等）のみ、ユーザーに相談する。

### 1-5. 抽出崩れレポート
- 分割と並行して、以下のパターンを洗い出して **[抽出崩れレポート]** として報告する：
  - 数式（分数、積分、上付き・下付き添字）
  - 単位記号（Ω、μ、℃、°）
  - ギリシャ文字（ω、φ、θ など）
  - 2段組の崩れ、表組みの崩れ
  - 図中ラベルの読み取り順序の混乱
  - 念校PDFで頻出した既知パターン（`Ω`→`X`、`μA`→`n A`、`φ`→`z`、`ω`→`~`、`選べ`→`選ベ`、伏せ字の`××`→`##` など）
- `ocr_quirks.md` の対応表をもとに、判明している崩れはレポート時点でマッピング表を提示
- これらは原本の誤記ではなく、PDF本文テキスト読み取りの制約として扱う

---

## ◆ Step 2/3: 用語集と表記ルールの作成

### 2-1. GLOSSARY.md の作成
- `glossary_template.md` を `Read` して雛形として利用
- 節ファイル群（または添付PDFの本文）を通読し、頻出用語（例：インピーダンス、力率、無効電力、三相交流、相電圧、線間電圧…）を抽出
- **表記ゆれ候補**（例：「インピーダンス/impedance」「力率 cosφ/cos θ」）は同じ用語の項目にまとめて列挙
- `output/<章名>/GLOSSARY.md` として保存

### 2-2. STYLE.md の作成
- `style_template.md` を `Read` して雛形として利用
- PDF全体から以下の表記ルールを抽出・記述：
  - 文体（「〜である」調／「〜です・ます」調）
  - 半角／全角（英数字、カッコ、記号）
  - 単位記号の扱い（`[Ω]` は半角角カッコか全角〔Ω〕か等）
  - 数式の書き方（インライン `I = V/R` 形式か LaTeX か）
  - フェーザ表記（V̇ などの上付きドットの慣例）
- `output/<章名>/STYLE.md` として保存

### 2-3. 完了報告（承認待ちしない）
- 両ファイルを出力後、以下のように**報告のみ**行い、**そのまま Step 3 に進む**：
  > `GLOSSARY.md` と `STYLE.md` を作成しました。引き続き Step 3（節ごと校正 ＋ REPORT.md 集約）に進みます。
- ユーザーが途中で編集したい場合は「止めて」と言ってもらう前提。デフォルトは無停止進行。

---

## ◆ Step 3/3: 節ごとの校正（全節を連続実行）

**全節（section01〜sectionNN）に対して、以下を順に自動実行する**。1節ごとにユーザー確認は求めず、全節の処理が終わったらまとめて完了報告する。

### 3-1. 読み込み
- 対象の節ファイル、`GLOSSARY.md`、`STYLE.md`、`ocr_quirks.md` をすべて `Read`
- `GLOSSARY.md` と `ocr_quirks.md` は全節で共通なので、1度読み込んだ内容を使い回してよい
- **該当節のページ画像は、添付PDFを直接視覚確認することで把握する**（`pages/page-NN.png` を別途生成する必要はない）。節が p.6〜p.13 なら、添付PDFのその範囲のページ画像をすべて確認する。

### 3-2. チェック観点（11項目）
1. **誤字脱字** — 文脈から明らかな誤字・脱字・送り仮名。**特に同音類字の取り違え**（例：「**定**電流」⇔「**低**電流」、「電**圧**降下法」⇔「電**圧**校下法」、「**測**定」⇔「**側**定」）は、文脈と組み合わせて明らかに矛盾する場合は原本誤記として指摘
2. **用語ゆれ** — `GLOSSARY.md` と照合。推奨表記と異なる箇所を指摘
3. **表記ゆれ** — `STYLE.md` と照合。文体・半角全角・単位表記の不一致を指摘
4. **数式記号の整合性** — 定義なしで使われた記号、ベクトル量なのに絶対値記号がない等
5. **文法・係り受け** — 主述のねじれ、修飾関係の曖昧さ、助詞の不自然さ（例：「磁束密度を 0 T **とする**のに必要な…」→「**にする**のに必要な…」）。**特に吹き出し・サイドノート・小キャラクターの解説では主語が省略されがちなので、「何を／誰が」が文中に現れているかを確認**（例：「分流器の倍率を大きくするには Ra よりずっと小さくすればよい」→ 主語の Rp が抜けている）
6. **単位・記号の明らかな誤記＋物理的整合性** — `V` と `A` の取り違え、`kW` と `W` の桁違い等に加え、**SI 組立単位・関係式のレベルで矛盾する単位記載**（例：表中で「コンダクタンス S = m⁻²·kg⁻²·s³·A²」と書かれているが、これは電気抵抗 Ω の逆数とすると kg の指数は `-1` でなければならない）。逆数関係・積関係にある量の組立単位が表内にあるなら、相互整合性をチェック
7. **章内整合性（クロスリファレンス）** — 章内の別の場所で示された分類表・定義表・公式と矛盾する記述がないか。特に：
   - **同一概念の物質分類**（例：「銅は反磁性体」と分類表で示されながら本文中で「常磁性体である銅」と書かれていないか）
   - **同一記号の多義使用**（例：`N` が場所により「総巻数」と「単位長当たり巻数」の両方で使われていないか）
   - **同一用語の定義揺れ**（例：本文では「ヒステリシス損失」で定義されているのに、後出箇所で「ヒステリシス損」になっていないか）
   - **同一公式の変数定義の矛盾**（例：直前の公式枠で `φ：磁束 / Φ：磁束鎖交数` と区別されたのに、次の公式枠で `φ：磁束鎖交数` と書かれていないか）
   - **章末問題への参照誤り**（例：本文中の NOTE「**後に登場する問題21の回路において**」とあるのに、実際の問題21 が NOTE の文脈と無関係な内容になっていないか）。本文中の「問題N」「上の問題」「次の問題」のような明示的参照は、参照先の問題の中身を確認して整合性をチェックする
   この観点は **Step 1 の節分割時にメモした「重要用語・分類・公式・問題番号の登場箇所」を Step 3 全体で参照しながら**チェックする
8. **過去問出典の重複検出** — 章末・節末問題に「H〇〇（問X）」「R〇〇上（問X）」のような出典表示がある場合、章内で**同一年度・同一問番号が2回以上現れたら必ずフラグ**を立てる。同年度・同問番号の問題が異なる内容で並列することは原理的にありえないため、いずれかが誤記の可能性が極めて高い。指摘の際は「両問題の問題内容（問題文の冒頭・与えられる数値）」を併記して，編集者が原典照合しやすくする
9. **念校プレースホルダの検出（DTP残り）** — 念校段階の原稿には、本来は実章番号・実ページ番号に置換されるべき**プレースホルダが多数残ることがある**。以下のパターンを章全体で grep し、残存箇所をすべて列挙する：
   - 「**第X章（p.XX）参照**」「**第 X 章**」（X が大文字英字のまま）
   - 「**p.XX**」「**P.XX**」「**pXX**」（XX が数字に置換されていない）
   - 「**p.__**」（アンダーバーのままのプレースホルダ）
   - 「**TODO**」「**◯◯**（記号）」「**未確定**」などのコメント
   一覧表形式で「箇所／PDF頁／文脈」を出力し、編集者が一括置換できるようにする。**プレースホルダ自体は `[要確認：DTP確認]` 分類とする**（原本の本文誤りではない）
10. **DTP残存オブジェクト（青下線・赤マーキング・コメントマーク等）の検出** — **添付PDFの各ページ画像を視覚確認した結果、本文中に**：
    - 校正用の青い下線（地の文の単語の下に引かれた青または別色の下線）
    - 校正用の赤マーキング、注釈マーク
    - 不自然な箇所のハイライト
    が残っている場合、これは **DTP/校正残りオブジェクト** の可能性が高い。**意図的な強調表記（オレンジ太字、メモチェ枠）と見分け、別カテゴリで指摘**する。「全本文の通常の強調と異なる種類のマーキングがある」と気づいた場合は、各ページ画像を確認して箇所を列挙し、`[要確認：DTP確認]` 分類で「残存オブジェクトであれば削除、意図的なら章全体で表記ルール統一」と提案する。
    - **重要**：青下線等は本文テキスト抽出には現れないため、**ページ画像視覚確認でしか検出できない**。Step 3 で各節のページ画像を見るときに必ずチェック観点に含める
11. **解説内の役割語・対応関係の自己矛盾** — 問題文・図・解説・解答の間で、同じ対象の役割が途中で入れ替わっていないかを確認する。特に回路・計器・電磁気の問題では、`電圧コイル` / `電流コイル`、`一次側` / `二次側`、`直列` / `並列`、`進み` / `遅れ`、`左手則` / `右手則` のような対になる語を全段落で追跡する。答えが合っていても、途中説明で役割名が逆転していれば `[原本の誤記]` または `[要確認：解説整合]` として指摘する

### 3-3. 抽出崩れとの区別
- `ocr_quirks.md` に記載のパターンに当てはまる場合は **[抽出ミスの可能性]** と明記し、指摘の優先度を下げる
- 当てはまらないパターン（明らかに原稿レベルで間違っている）は **[原本の誤記]** と明記
- **n ⇔ μ パターン等の判断保留指摘は、Codex 等の別 AI による画像視覚確認結果が `extraction_notes.md` や Codex 側 `corrections_*.md` に「ページ画像で正常表示を確認」のような形で記載されていれば、それを根拠に「抽出ミス確定（修正不要）」と分類を変更してよい**。Step 4 の Codex レポート統合時に行う

### 3-3b. 図・表に関する指摘の厳格ルール（最重要）
- 図（`図 1-N`）、表（`表 1-N`）、回路図、グラフ、ベクトル図などに関する指摘を出す前に、**必ず添付PDFの該当ページを視覚確認する**
- 本文抽出テキストの断片的な数値・ラベル・文字列だけを根拠に、図の構造や数値の並びを推測してはならない（PDFの本文テキストは図中の文字を断片的にしか拾えないため、読み取りミスの温床）
- 視覚確認した上でも判定できない場合は **[要確認：図の原本目視確認]** として、断定的な「誤」表現を避ける
- 「図 N-M の〜〜が誤り」と書く指摘は、必ず添付PDFのページ画像を確認した上で出すこと。確認していない場合はその指摘自体を取り下げる
- 図キャプションの表現（「電圧」と「電流」の取り違えなど）は本文と照らし合わせて整合性をチェックする

### 3-4. 出力
- `correction_template.md` のフォーマットに従い、`output/<章名>/corrections/corrections_sectionNN.md` として保存
- 指摘がゼロの場合は「修正が必要な箇所は見つかりませんでした。」と出力

### 3-5. 全節完了時のサマリ
全節の処理が終わったら、以下の形でまとめて報告する：

> ✅ 全N節の校正が完了しました。
>
> | 節 | タイトル | 指摘件数 | 原本誤記 | 抽出ミス疑い | 要確認 |
> |----|---------|---------|---------|-------------|--------|
> | section01 | 4-1 交流のキホン | 7 | 5 | 0 | 2 |
> | section02 | 4-2 交流回路のキホン | 6 | 5 | 0 | 1 |
> | ... | ... | ... | ... | ... | ... |
>
> 詳細は各 `output/<章名>/corrections/corrections_sectionNN.md` をご確認ください。
>
> この章に電験三種の過去問が含まれる場合、以下のコマンドで追加の深堀り校正（計算検証・法令照合・ファクトチェック）が取得できます：
>
>     /denken3-proof <添付PDFの該当箇所> [年度・問番号]

### 3-6. 全節集約レポート REPORT.md の出力（**必須**）

全節のサマリ報告と**同時に**、1枚のレポートを `output/<章名>/REPORT.md` として**必ず出力する**。チャット上のサマリ表だけで終わらせず、ファイルとして残す。

`REPORT.md` の構成は以下の5セクション：

1. **全体サマリ**
   - 対象PDF、照合ファイル、総指摘件数（原本誤記 N 件 / 要確認 N 件 / DTP確認 N 件）
   - 視覚確認の方法（「チャット添付PDFのページ画像で実施」と明記）
   - 節別の件数一覧表：`| 節 | タイトル | 原本誤記 | 要確認 | DTP確認 | 主な論点 |`

2. **🔴 最優先修正項目（原本誤記）**
   - 重要度（★★★ ロジック・数式・物理単位の誤り／★★ 記号・表記の誤り／★ 軽微）で分類
   - 各項目は `#連番 — sectionNN / p.XX（文脈）`／`誤：`／`正：`／（理由・根拠）／`観点：` の構成

3. **🟡 要確認項目（判断保留）**
   - 表形式：`| # | 位置 | 内容 | 観点 |`

4. **🔧 DTP確認項目（念校段階の残存）**
   - **プレースホルダ参照**（「第X章（p.XX）」「P.XX」等）の残存箇所を一覧化（PDF頁・文脈付き）。最終版前に編集者が一括置換できるリストにする
   - **本文中の校正残りオブジェクト**（青下線・赤マーキング等）の残存箇所を一覧化。視覚確認したページ番号と該当語句を併記
   - これらは「原本の本文誤り」ではないため最優先項目とは別枠で集計

5. **指摘対象外（参考情報）**
   - PDF抽出の機械的崩れの除外方針を明示
   - 計算問題の検算結果サマリ（出典・解答の整合チェック結果を表形式で）

6. **推奨される次のアクション**
   - 修正優先順位の示唆
   - `/denken3-proof` で追加校正できる問題の例示

`REPORT.md` 出力前に、必ず以下の整合確認を行う：

- `sections/sectionNN.txt` と `corrections/corrections_sectionNN.md` の数が一致しているか
- `REPORT.md` の総件数が各 `corrections_sectionNN.md` の件数合計と一致しているか
- `第X章`、`第 X 章`、`p.XX`、`P.XX`、`p.__`、`TODO`、`未確定`、`確認` などの未処理文字列が成果物に残っていないか
- 画像確認が必要な図・表・DTP残存オブジェクトの指摘に、確認ページまたは確認不能理由が書かれているか
- 旧章名・旧出力先・テンプレートのサンプル文が混入していないか

レポート末尾に「節別の詳細（根拠・画像確認状況）は `corrections/corrections_section01.md` 〜 を参照」と誘導を付ける。

## ◆ Step 4/3（任意）: Codex等の他ツール出力との統合レポート `REPORT_merged.md`

REPORT.md を出力した直後に，**同じ原稿に対して別ツール（Codex 等）が出力したレポートが存在しないか**を自動探索する。見つかれば，両者を並置した統合レポート `REPORT_merged.md` を生成する。

### 4-1. Codex レポートの探索（自動）

以下のパターンを Glob で確認する（ヒットしなければスキップ）：

- `…/<同じ章名 or 原稿名>_codex*/REPORT.md`（denken3-pastexam-proof と同じ規約）
- `…/<原稿名>_Codex校正/REPORT.md`
- `…/Codex出力/<章名>/REPORT.md` `…/Codex/<章名>/REPORT.md`
- ユーザーが直近に開いていたファイル（IDE-opened）に「codex」を含む REPORT.md が含まれていればそれを採用

最初の3パターンは添付PDFのファイル名（`アカデミア_理論_念校pdf（3章）.pdf` → `アカデミア_理論_3章` / `アカデミア_理論_念校_3章` などのバリアント）に対して試す。**配置場所は `OneDrive/30_AI/開発/電験三種/`、`OneDrive/10_電気工学/.../Codex出力/`、プロジェクトルート直下など複数あり得る**ため、ユーザーホーム配下の OneDrive ツリー全域を Glob 対象にする。

見つからない場合は何もしない（黙って Step 4 をスキップ）。**ユーザーに確認を取らない**（スキップしたことすら報告しない）。

### 4-2. 統合レポートの作成

Codex レポートが見つかったら、それと自身の `REPORT.md`、両者の `corrections/corrections_section*.md` をすべて読み込み、`REPORT_merged.md` を以下の構成で生成する：

1. **両AIが独立に指摘した項目（最優先・確度高）** — Codex #N と Codex #M の対応表。両者一致は紙面修正の最優先候補
2. **Codex 単独で指摘・Codex 未指摘** — 表形式（Codex が得意な領域：GLOSSARY/STYLE 照合、章内クロスリファレンス、物理単位の整合性、同音類字の誤字）
3. **Codex 単独で指摘・Codex 未指摘** — 表形式（Codex が得意な領域：DTP残存オブジェクト＝青下線・残存マーキング、プレースホルダ参照、図中の細部確認など、**ページ画像視覚確認に強い領域**の指摘がここに集まりやすい）
4. **紙面修正優先順位（統合版）** — 両者一致 ＞ 物理・論理の誤り（章内整合性違反含む）＞ DTP残存（プレースホルダ参照・青下線）＞ 用語・整合性 ＞ 編集判断 の段階で並べ直す
5. **検算結果** — 両レポートで結果が一致した問題は「両者一致」と注記
6. **出力ファイル一覧** — Codex側／Codex側の双方のディレクトリ構造を表示

### 4-3. 報告

`REPORT_merged.md` を生成した場合のみ、最後に一文添える：

> 同じ原稿に対する Codex レポートを `<検出パス>` に検出しました。統合版 `REPORT_merged.md` を出力しています。

ユーザーから後追いで「Codex のレポートもあります」と渡された場合は、Step 4 を単独で実行する（Step 1〜3 は再実行しない）。

## エラー・失敗時の挙動

| 失敗パターン | 対処 |
|-------------|------|
| 添付PDFがファイルパス指定で渡された | 「PDFをチャットに直接添付して再送してください」と案内（このスキルはチャット添付前提） |
| 添付PDFが画像ベース（スキャン）で本文テキストが取れない | 「OCRをかけたPDFを再送してください」と伝えて中断 |
| 節見出しが検出できない | ページ数ベースで均等分割（5ページ単位）に切り替え、ユーザーに相談 |
| 図中の文字や数式の細部が画像確認でも読み取れない | `[要確認：図の原本目視確認]` として、断定的な指摘を避ける |
| 数式・単位記号の崩れ多発 | `ocr_quirks.md` で自動補完。対応表にないパターンは「要確認」として指摘 |
| 用語抽出が過多／過少 | `GLOSSARY.md` は編集歓迎である旨を案内し、ユーザーのフィードバックで調整 |
| 40ページを大きく超える（章が1ファイルに収まっていない） | 警告を出し、章単位で分割してから再度添付するよう依頼。処理時間とコンテキスト消費が大きくなる旨を説明 |
| 既存 `output/<章名>/` がある | 上書き確認を取るか、別名（`<章名>_v2` など）で保存 |
| Codex レポートが見つからない | 黙ってスキップ。ユーザーに確認を取らない |
| Codex レポートが複数見つかった | 最も新しいタイムスタンプのものを採用し、検出パスを `REPORT_merged.md` 冒頭に明記 |
| Codex レポートが PDF 形式（Markdown でなく PDF） | 添付PDFと同じ手順で本文を読み取り、`<検出パス>/REPORT.md` に相当する内容として扱う |
| ユーザーから後追いで「Codex のレポートもあります」と渡された | Step 4 を単独実行（Step 1〜3 は再実行しない）|

## `/denken3-proof` との役割分担

| | このスキル（pdf-proofreading） | `/denken3-proof` |
|---|---|---|
| 対象規模 | 1章分（最大40ページ前後） | 単一の問題PDF |
| 主な強み | 用語ゆれ・表記ゆれの横断検出、節分割、図キャプションの整合性チェック | 計算検証、法令照合、ファクトチェック |
| 使いどころ | 1章の一次校正 | 問題解説の最終チェック |

本スキルで節分割と一次校正まで行い、問題を含む節に対しては別途 `/denken3-proof` を実行することで、両者を補完的に活用する運用を推奨する。

## 旧運用（pdftotext / pdftoppm を使う運用）からの移行メモ

このスキルは以前、Poppler 同梱の `pdftotext`（テキスト抽出）と `pdftoppm`（ページ画像化）を使ってPDFを処理する設計だった。現在は **チャット添付PDFをCodexが直接読み取る運用** に切り替えたため、これらの外部ツールは不要。

旧運用の利点：
- ファイルシステム上にPDFを置いてバッチ的に処理できる
- ページ画像（`pages/page-NN.png`）を成果物として残せる

新運用（チャット添付）の利点：
- 外部ツールのインストール不要
- 添付PDFの本文テキストと画像を Codex が同時に読み取れる（精度が高い）
- 図キャプションの誤記など、画像視覚確認が必須の指摘が確実にできる
- ファイルパスの文字化け（日本語ファイル名）に悩まなくて済む

そのため、**新運用が標準**。旧運用に戻す必要が出た場合（バッチ処理など）は、`pdftotext -layout` と `pdftoppm -png -r 200` を Bash で実行して `pages/` フォルダに画像を残すパスもサポートできる。

Codex 等でローカルPDFパスを扱う場合は、Poppler が PATH に無いことが多いため、`pdfinfo.exe` / `pdftotext.exe` / `pdffonts.exe` / `pdftoppm.exe` の実体パスを探索して使う。Windows PowerShell では実行前に `[Console]::OutputEncoding=[System.Text.Encoding]::UTF8` を設定し、日本語パスとPoppler出力の文字化けを避ける。抽出方法・警告・見開き/面付けの有無・ページ画像確認の限界は `raw/extraction_notes.md` に必ず残す。
