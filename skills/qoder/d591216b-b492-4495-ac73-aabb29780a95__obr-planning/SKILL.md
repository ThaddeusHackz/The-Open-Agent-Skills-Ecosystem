# OBR 制定与进展填写

## 概述

OBR = Object（目标用户+痛点）+ Behavior（关键行为）+ Result（关键结果）。
本技能帮助用户：
1. **制定月度OBR**：将粗略想法转化为符合OBR方法论的标准计划
2. **填写进展review**：将双周/月末完成事项整理为规范的进展描述

---

## 模式一：制定月度OBR

### 步骤1：收集基础信息

通过 AskUserQuestion 收集：

**问题1：OBR周期**
- 哪个月份？（如：2026年8月）

**问题2：OBR数量**
- 本月计划设定几个O（Object）？建议1-3个

**问题3：每个O的基础信息**（逐O收集）
- 面向哪些具体用户群体？
- 用户当前面临什么核心痛点？
- 计划通过哪些事项/行为来解决？
- 期望达成什么可衡量的结果？

### 步骤2：质量校验与澄清

对每个O进行以下校验，不通过时用 AskUserQuestion 澄清：

| 校验项 | 标准 | 常见问题 |
|--------|------|----------|
| O用户画像 | 具体到角色/岗位，非泛泛而谈 | "业务研发"→"负责采购模块的后端研发" |
| O痛点表述 | **用户可理解的语言**描述困扰，禁止技术术语堆砌 | "缺SDK"→"每次对接数据层都要手写，重复造轮子，新人上手要3天" |
| B用户视角 | B的描述要让**用户看得懂得到了什么**，而非只写技术实现 | "交付BaseMapper SDK"→"交付标准化数据访问工具，让业务研发不再手写CRUD" |
| B数量 | 每个O对应2-3个B | 超过3个需合并或拆分 |
| R用户效果 | R必须包含**用户视角的效果指标**：不仅"可用"，还要"好用/可靠" | 只有"接入通过率100%"→还需补充"接入人日降至0.5天、接入文档满意度≥4分" |
| R因果性 | R能直接验证B是否解决了O的痛点 | R与B脱节，需重新对齐 |
| B/R映射 | **允许多个B共同对应一个R**，不必每个B单独配R | 当多个B是同一目标的不同实现路径时，应共享R |
| 月度可达性 | B和R在一个月内可验证 | 范围过大需缩小到本月可交付的最小闭环 |

**澄清问题模板**：
- "O[编号]的用户画像可以更具体一些，是面向[选项A]还是[选项B]？"
- "B[编号]的当前基线数据是多少？目标值期望达到多少？"
- "这个B本月能完成吗？还是需要缩小范围到[具体子集]？"

### 步骤3：生成OBR表格

按模板格式生成xlsx文件。

**表头结构（13列）**：

| 列 | 字段名 | 填写要求 |
|----|--------|----------|
| A | 月份 | 月份名称（如：8月） |
| B | O（具体用户） | 按O合并单元格 |
| C | O（解决用户的痛点/增量价值） | 按O合并单元格，用户视角描述 |
| D | OBR责任人 | 按O合并单元格 |
| E | B（关键行为） | 每B一行，编号格式：O1-B1、O1-B2... |
| F | R（关键结果） | B与R可以是1:1或N:1关系。当多个B共享同一R时，仅在第一个B行写明R描述，其余B行写"同O1-R1"并合并单元格。编号格式：O1-R1、O1-R2... |
| G | B责任人 | 每B的负责人 |
| H | 月中进展&风险 | 月中时填写，制定时留空 |
| I | 月中进展review纪要 | 月中时填写，制定时留空 |
| J | 月末进展&风险 | 月末时填写，制定时留空 |
| K | 月末进展review纪要 | 月末时填写，制定时留空 |
| L | B进展状态 | 下拉：进行中-正常/进行中-delay/完成，制定时默认"进行中-正常" |
| M | O进展状态 | 按O合并单元格，制定时默认"进行中-正常" |

**O表述格式**：
- B列：【用户画像】，如"负责采购模块的后端研发人员"
- C列：O[编号]解决[具体痛点描述]，如"O1解决每次对接数据层都要手写CRUD、重复封装、新人上手慢的痛点"

**B表述格式**：
- E列：O[编号]-B[编号]（行为名称）：具体行为描述
- 行为必须是可执行的动作，如"交付"、"上线"、"跑通"、"完成验收"
- 包含明确的交付物和验证标准

**R表述格式**：
- F列：O[编号]-R[编号]（结果名称）：基线→目标；具体指标描述
- 必须包含可衡量的数字或可验证的状态变化
- **必须包含用户视角的效果指标**：不仅衡量"是否可用"，还要衡量"是否好用、可靠"
  - 效率指标：如接入耗时从X天降至Y天
  - 可靠性指标：如关键路径自测通过率、线上故障率
  - 体验指标：如接入文档易用性评分、用户满意度
- B与R多对一时：仅在第一个B行写完整R描述，其余B行的F列写"同O[编号]-R[编号]"，并在xlsx中合并对应F单元格
- 示例："O1-R1（开发效率与体验提升）：标准CRUD接入从「各自封装约3天」→「基于SDK 0.5天完成」；试点模块接入自测通过率100%；接入文档经2名业务研发验证，评价'开箱即用'"

### 步骤4：生成xlsx文件

使用 openpyxl 生成符合模板格式的xlsx文件：

```python
from openpyxl import Workbook
from openpyxl.styles import Alignment, Font, PatternFill, Border, Side
from openpyxl.utils import get_column_letter

wb = Workbook()
ws = wb.active
ws.title = month_name  # 如 "2026-8"

# 表头
headers = ["月份", "O（具体用户）", "O（解决用户的痛点/增量价值）", "OBR责任人",
           "B（关键行为）", "R（关键结果）", "B责任人",
           "月中进展&风险", "月中进展review纪要",
           "月末进展&风险", "月末进展review纪要",
           "B进展状态", "O进展状态"]

# 写入数据并合并单元格
# 同一O的B/C/D/M列需要跨行合并
```

**合并规则**：
- 同一O的多个B共享：月份(A)、O用户(B)、O痛点(C)、OBR责任人(D)、O进展状态(M)
- 这些列在O内合并为一个单元格

**样式要求**：
- 表头：背景色 #D9E1F2，居中，自动换行
- 数据行：自动换行，垂直居中
- 列宽：A=8, B=25, C=35, D=12, E=50, F=45, G=10, H-K=30, L-M=15

## 模式二：填写双周/月末进展

### 步骤1：确认填写周期

通过 AskUserQuestion 确认：

**问题1：填写类型**
- 月中进展（第2周）还是月末进展（第4周）？

**问题2：涉及的O和B**
- 本次需要更新哪些O/B的进展？

### 步骤2：收集进展信息

对每个B收集：

**关键行为进展**：
- 本周期完成了什么？
- 正在进行什么？
- 待办事项？

**关键结果数据**：
- 当前指标数据（过程指标+结果指标）
- 与基线/目标的对比

**风险揭示**（如有）：
- 投入不足？技术瓶颈？时间周期？协同问题？

### 步骤3：格式化进展描述

**月中/月末进展&风险** 统一格式：

```
【关键结果进展】
1. [指标1]：当前值X（基线Y，目标Z）
2. [指标2]：定性描述

【关键行为进展】
1. 已完成：[具体交付物]
2. 进行中：[当前状态]
3. 待办：[下一步计划]

【风险揭示】（如无则写"暂无"）
1. [风险描述]，应对措施：[具体对策]
```

### 步骤4：更新xlsx文件

- 读取已有OBR表格
- 找到对应的B行
- 在对应列（H/I 或 J/K）填入进展内容
- 更新L列（B进展状态）和M列（O进展状态）
- 保存文件

## OBR质量原则速查

### 好的O vs 差的O

| 差（任务驱动 / 技术语言） | 好（价值驱动 / 用户语言） |
|----------------|----------------|
| "上线XX功能" | "为[具体用户]解决[核心痛点]" |
| "重构底层架构" | "解决[某场景]下[具体性能/体验问题]" |
| "统一数据访问层SDK" | "让业务研发不再各自封装数据访问，新人半天上手" |

### 好的B vs 差的B

| 差（技术任务 / 用户看不懂） | 好（用户看得懂得到了什么） |
|----------------|------------------|
| "交付BaseMapper SDK" | "交付标准化数据访问工具，让业务研发不再手写CRUD" |
| "写代码做测试" | "完成自测验收，业务研发可直接使用，关键路径通过率100%" |
| "重构查询引擎" | "优化复杂查询性能，让大客户月底导出报表不再卡顿" |

### 好的R vs 差的R

| 差（只有可用性指标） | 好（包含用户效果指标） |
|----------------|------------------|
| "接入通过率100%" | "接入从3天降至0.5天，接入文档经业务研发验证'开箱即用'" |
| "SDK已发布" | "SDK已发布，2个试点模块成功接入，业务研发反馈'显著减少重复代码'" |
| "按时上线" | "试点应用接入通过率100%，线上运行2周零故障" |

### B/R多对一映射示例

当多个B服务于同一个用户价值目标时，可共享R：
```
O1-B1（查询SDK）  →  O1-R1（数据访问标准化与效率提升）
O1-B2（CRUD服务SDK）→  同O1-R1（合并单元格）
O1-B3（元数据上报）  →  O1-R2（能力可发现闭环）
```
判断依据：如果多个B的完成共同贡献于同一个用户可感知的结果，就应共享R。

### 因果验证

每个R都要问自己：
- "如果B完成了，R是否会发生？" → 验证B→R因果
- "如果R达成了，O的痛点是否被解决？" → 验证R→O因果

## 输出要求

1. **文件格式**：xlsx（使用 openpyxl）
2. **文件命名**：`OBR跟进表格-[团队名]-[月份].xlsx`
3. **工作表名**：月份标识（如 "2026-8"）
4. **合并单元格**：同一O的A/B/C/D/M列必须跨B行合并
5. **自动换行**：所有数据单元格启用 wrap_text
6. **列宽**：按上述样式要求设置
