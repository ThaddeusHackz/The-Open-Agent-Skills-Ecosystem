# 更新迭代测试用例

## 触发场景

- 用户说"tasks.md 更新了，帮我更新测试用例"
- 用户说"帮我根据最新任务更新用例"
- 迭代过程中需求/任务有变动

## 规则依据

更新测试用例时，同样遵循三层规则体系：
- 全局规则：`../generate-test-cases/rules/global.md`
- 项目规则：`../generate-test-cases/rules/project.md`
- 迭代规则：`../generate-test-cases/rules/iteration.md`

新增用例时按规则要求补充权限校验、边界条件等；修改用例时确保仍符合规则约束。

## 执行流程

### Step 1：拉取最新代码

```bash
cd c:\TestTools\code\busyming-mcp-service
git pull --rebase
```

### Step 2：检测版本并确认

检查 `product-project/` 目录下的版本目录数量：

- **单个版本**：自动使用
- **多个版本**：询问用户要更新哪个版本的测试用例

询问示例：
> 检测到多个版本目录：v20260624-0.1、v20260628-0.2
> 请问要更新哪个版本的测试用例？

确认后，仅对比该版本目录下的 tasks.md 变更。

> 用户选择的版本记为 `{version}`，后续所有步骤中的路径均使用此变量。若用户未指定版本且仅存在一个版本目录，则自动使用该版本。

### Step 3：对比 tasks.md 变更

对比方式（按优先级选择）：

**方式 A：Git diff 对比**
```bash
git diff HEAD~1 -- product-project/{version}/*/tasks.md
```
或指定具体 commit 范围：
```bash
git diff <旧commit>..<新commit> -- product-project/{version}/*/tasks.md
```

**方式 B：与本地缓存对比**
如果用户提供了上次生成用例时的 tasks.md 快照，直接做文本差异对比。

**方式 C：用户指定变更**
用户直接告知哪些模块的 tasks.md 有变更。

### Step 4：分析变更类型

对比 tasks.md 后，识别以下变更类型：

| 变更类型 | 含义 | 对测试用例的影响 |
|---------|------|----------------|
| 新增任务 | tasks.md 中新增了一项任务 | 需要新增对应的测试用例 |
| 修改任务 | 已有任务的描述/验收标准变了 | 需要修改对应的测试用例 |
| 删除任务 | 原有任务被移除 | 需要删除或标记为废弃对应的测试用例 |
| 状态变更 | 任务状态从 TODO→DONE 等 | 不影响测试用例内容 |

### Step 5：读取相关上下文

对于有变更的模块，读取：
1. 该模块的 `spec.md` — `product-project/{version}/{模块}/spec.md`
2. 该模块的 `checklists/requirements.md` — `product-project/{version}/{模块}/checklists/requirements.md`
3. 该模块的 `tasks.md`（最新版）— `product-project/{version}/{模块}/tasks.md`
4. Demo 参考 — `product-project/{version}/mcp应用平台-demo/`

### Step 6：更新测试用例

根据变更类型，同步更新两个版本：

**新增任务** → 在对应模块的测试文件末尾追加新用例
**修改任务** → 找到对应的测试用例，修改步骤/预期结果
**删除任务** → 删除对应的测试用例，调整编号

**数据准确性校验检查**：当新增/修改的模块涉及后端数据查询展示（如列表、统计、详情接口），更新的测试用例中必须包含"造数据→查询→逐字段验证"类型用例，确保覆盖字段值精确匹配、统计计算准确性、排序正确性和分页准确性。参考 `global.md` 第十二条规则。

更新路径：
- AI 执行版：`test-project/ai-version/{模块编号}-{模块名}.md`
- 人工阅读版：`test-project/manual-version/{模块编号}-{模块名}.md`

### Step 7：输出变更报告

更新完成后，输出一份变更摘要：

```markdown
## 测试用例变更报告

### 变更来源
- 模块：{模块名}
- tasks.md 变更类型：新增/修改/删除
- 变更内容摘要：...

### 测试用例变更
| 操作 | 用例ID/编号 | 变更说明 |
|------|-----------|---------|
| 新增 | TC-XXX-001 / 编号 28 | 覆盖新增的 XXX 功能 |
| 修改 | TC-XXX-002 / 编号 15 | 更新验收标准 |
| 删除 | TC-XXX-003 / 编号 10 | 对应任务已移除 |

### 影响统计
- 新增用例：X 条
- 修改用例：X 条
- 删除用例：X 条
- 当前总用例数：XXX 条
```

## 双版本同步规则

任何更新必须同时作用于 AI 执行版和人工阅读版：
- AI 版格式：TC-ID、前置条件、步骤、断言、优先级
- 人工版格式：中文表格（编号/场景/步骤/预期结果）
- 禁止只更新一个版本

## 权限校验检查

如果变更涉及新增页面或新功能模块，检查是否需要登录：
- 如需登录，必须追加 6 类权限校验用例（未登录拦截、企微登录、账号密码登录、错误密码、登录态过期、无权限用户）

## 编号处理

- 新增用例：编号追加在该模块已有用例末尾
- 删除用例：后续编号不重排（避免与已有记录冲突），在 AI 版中标记为 DEPRECATED 或直接删除
- 修改用例：保持原编号不变

## 文案质量检查规则

更新测试用例时，必须确保每个模块包含文案质量检查用例（`TC-E2E-TEXT-*` 前缀）：

- 若模块已有文案检查用例 → 检查是否需随变更更新
- 若模块缺少文案检查用例 → 必须补充，覆盖5类维度（错别字、逻辑通顺、中英文混排、文案一致性、空文案/占位符）
- 详细规则参见 `../generate-test-cases/rules/global.md` 第十三章

## 多账号交叉验证规则

更新测试用例时，若模块涉及密钥/凭证、用户数据隔离、权限角色差异、并发操作、用户间交互、配额限额等场景，必须包含多账号交叉验证用例（`TC-E2E-ISO-*` 前缀）：

- 若模块已有隔离性用例 → 检查是否需随变更更新
- 若模块涉及上述场景但缺少隔离性用例 → 必须补充，覆盖4个维度（数据隔离性、独立操作性、操作隔离性、唯一性验证）
- 详细规则参见 `../generate-test-cases/rules/global.md` 第十四章

## AI推荐相关性用例更新检查（引用 global.md 第十七章）

更新测试用例时，如涉及AI推荐、搜索结果准确性类用例，必须检查并确保：

1. **查询关键词区分度**：用例中的搜索/问答关键词是否具有高区分度（能区分相关与不相关结果）
   - 如果使用泛关键词（如"检测"、"图片"、"服务"），必须替换为意图明确的特定查询
2. **断言完整性**：预期结果是否同时包含"应包含"和"不应包含"两个方向
   - 如果仅有正向断言（应包含XX），必须补充负向断言（不应包含YY及原因）
3. **判定逻辑语义化**：判定标准是否深入业务语义层面
   - 如果判定逻辑为"名称包含关键词"这类字面匹配，必须改为语义匹配判定

违反上述规则的用例在更新时必须同步修正。

### AI响应内容安全用例更新检查

更新测试用例时，如涉及"无结果"、"不存在"、"兜底回复"类场景的用例，必须检查并确保：

1. **响应安全断言完备性**：用例是否包含"不得暴露内部服务名"、"不得推荐调用内部工具"、"不得使用夸大表述"三项强制断言
   - 如果仅验证"是否提示无结果"而无响应安全断言 → 必须补充
2. **检查视角正确性**：预期结果是否从终端用户视角出发
   - 如果预期结果中允许出现开发者/内部术语 → 必须修正为面向用户的友好表述
3. **异常判定完整性**：是否明确标注"暴露内部信息=Bug(P1)"
   - 如果无此判定规则 → 必须补充

违反上述规则的用例在更新时必须同步修正。

### 环境自适应用例更新检查

更新测试用例时，如涉及数据量触发类功能（分页、查看全部、加载更多等），必须检查并确保：

1. **前置条件无硬编码数量**：前置条件中是否包含具体数字（如">6"、"超过10条"）
   - 如果存在硬编码数量条件 → 必须改为动态观察模式
2. **双分支覆盖**：用例是否同时覆盖"条件满足"和"条件不满足"两种路径
   - 如果仅有单分支（只验证触发时的行为） → 必须补充未触发时的反向验证
3. **环境可执行性**：用例是否在任何数据量环境下都能执行（即使走不同分支）
   - 如果用例会因数据不足被整体跳过 → 必须重构为双分支自适应结构

违反上述规则的用例在更新时必须同步修正。

## 注意事项

- **临时脚本/文件清理**：执行过程中若生成了临时脚本或临时文件（如 `.tmp-*.json`、`.py` 辅助脚本等），任务完成后必须立即删除，不得留在项目目录中

- 只更新有变更的模块，不动其他模块
- 如果 tasks.md 变更较大（如整个模块重构），建议整体重新生成而非逐条修改
- 更新后同步更新 test-project/README.md 中的用例总数
- product-project 的 spec.md、plan.md、tasks.md、requirements.md 本身不做修改
