# 产品思考提取器

从带教相关录音的转录文本中，提取可学习的产品思维和洞察。

## 录音来源说明

转录文本的来源不限于用户与带教的一对一谈话，也包括：
- 带教带用户参加的业务会议
- 团队内部评审、讨论会
- 任何带教参与的、涉及产品讨论的场合

处理时不要假设只有两个说话人。会议录音可能有多人发言，需根据上下文判断各发言人身份。

## 核心原则（强制）

**涉及产品思考的内容，必须附带完整原文。** 所谓"完整"是指：不能只摘一句金句，而是要把围绕该产品思考的整段讨论原文都罗列下来，包括上下文、追问、举例等，让读者能还原当时的思考脉络。宁多勿少。

## 使用流程

### Step 1: 获取转录文本

如果用户提供的是音频文件（mp3/m4a/wav/flac 等），通过钉钉 AI 听记上传获取转写：

```bash
# 1a. 获取文件大小（字节）
stat -f%z "<音频文件路径>"

# 1b. 创建上传会话
dws minutes upload create --file-name "<文件名>" --file-size <字节数> --format json
# 返回 presignedUrl 和 sessionId

# 1c. 上传文件到 presignedUrl（注意：不加 Content-Type header，否则报403）
curl -s -w "\n%{http_code}" -X PUT -T "<音频文件路径>" "<presignedUrl>"
# 确认返回 200

# 1d. 确认上传完成，获取 taskUuid
dws minutes upload complete --session-id "<sessionId>" --format json
# 返回 taskUuid

# 1e. 等待转写完成后拉取转写原文（刚上传需等 20-30 秒）
dws minutes get transcription --id <taskUuid> --format json
# 如果 paragraphList 为空，等待后重试
```

如果用户已有文字稿或钉钉听记链接，直接进入 Step 2。听记链接按 `minutes-insight-to-doc` 技能的方式提取 taskUuid 后拉取转写。

### Step 2: 识别说话人

尝试从上下文区分带教（mentor）和实习生（intern）的发言。标记依据：
- 带教通常在解释原因、分享经验、提出框架
- 实习生通常在提问、确认理解

如果无法区分，标注为"未识别说话人"并继续。

### Step 3: 提取内容

从转录文本中识别以下类型的内容：

**A. 产品决策逻辑** — 为什么做/不做某个功能，如何权衡取舍
**B. 用户洞察** — 对用户行为、需求、心理的观察
**C. 方法论/框架** — 可复用的思考模型或工作方法
**D. 行业认知** — 对市场、竞品、趋势的判断
**E. 踩坑经验** — 曾经犯过的错误和教训
**F. 价值观/原则** — 做产品的底层信念

### Step 3.5: 识别"亮眼原话"（强制执行）

在提取内容的同时，标记出必须"一字不改保留"的原话。识别信号：

- 金句式短语（对仗、比喻、反常识）
- 观点密度高（一句话讲清一个决策/原则）
- 有情绪或强调（"我告诉你"、"记住"、"最重要的是"）
- 反直觉或颠覆既有认知的表达
- 未来可能被反复引用的话

**处理规则**：
1. 一字不改抄录进"亮眼原话"区，保留口语化表达（"嗯"、"你懂吧"等特色语气词也保留）
2. 用「」包裹，附上说话时的背景
3. 严禁改写、润色、缩写、翻译成"更书面"的表达
4. "原话区"与"我的理解"区必须视觉上明确分离
5. 拿不准是否为原话时：标 `[大意]` 表转述，或标 `[?]` 让用户确认；绝不把转述伪装成原话

### Step 4: 输出三种格式

#### 格式零（最优先）：亮眼原话原文库

在所有输出的最前面，先呈现"必须原样保留"的原话集。此区域只放原文，不做任何解读。

模板：

```markdown
## 🌟 亮眼原话（一字不改）

> 「[mentor 原话，完整保留，含语气词]」
> —— 背景：[什么讨论中说的]
> —— 归类：[六维中的哪一类，如"产品决策逻辑"]

> 「[另一句原话]」
> —— 背景：[...]
> —— 归类：[...]

## 💭 对上述原话的理解与延伸
（跟原话区严格分开；这里才是解读）

**关于第 1 句**：[用自己的话复述含义] · [可以怎么用]
**关于第 2 句**：...
```

#### 格式一：结构化笔记

按上述六个维度分类整理，每个条目包含：
- 核心观点（一句话）
- 上下文（当时在讨论什么）
- 原话摘录（如有明确表述）
- **产品思考原文段落**（强制）：把涉及该产品思考的完整对话段落原文粘贴在此，包含上下文、追问、举例等，不得省略或缩写

模板：

```markdown
## 结构化笔记

### 产品决策逻辑
1. **[核心观点]**
   - 背景：[讨论什么时提到的]
   - 原话：「[关键表述]」

### 用户洞察
...

### 方法论/框架
...

### 行业认知
...

### 踩坑经验
...

### 价值观/原则
...
```

#### 格式二：金句 + 思考摘要

提取最有启发性的 5-10 句话，每句附带：
- 原文金句
- 我的理解（用自己的话复述）
- 可以怎么用（应用场景）

模板：

```markdown
## 金句与思考

### 1. 「[原文金句]」
**我的理解**：[用简单的话解释这句话的意思]
**可以怎么用**：[在什么场景下可以应用这个思考]

---
```

#### 格式三：学习卡片

每张卡片聚焦一个可学习的洞察：

模板：

```markdown
## 学习卡片

---
### 卡片 #1: [简短标题]
| 维度 | 内容 |
|------|------|
| 观点 | [一句话核心观点] |
| 背景 | [什么情境下说的] |
| 为什么重要 | [对做产品有什么帮助] |
| 我能怎么用 | [具体行动建议] |
| 关联知识 | [相关的产品概念或书籍] |

---
```

### Step 5: 生成总结

在文档最后附上：
- **本次对话主线**：这次谈话的核心话题是什么
- **最重要的 3 个收获**：如果只能记住三件事
- **待深入了解的问题**：谈话中提到但还没完全理解的点

### Step 6: 写入钉钉文档（子文档模式）

提取完成后，将结果写入钉钉文档。**必须以子文档形式写入父文档下**，而非直接追加到父文档正文。

**父文档**（已固定）：nodeId=dQPGYqjpJYZnRbNYCBxPjo448akx1Z5N（title:会议纪要）

```bash
# 6a. 将提取结果写入临时文件
# （将 Step 4 + Step 5 的完整 Markdown 内容写入 /tmp/product_thinking_<标题>.md）

# 6b. 在父文档下创建子文档（子文档名 = 听记中最核心、最抓人的那个产品思考点）
dws doc create --name "<最核心的产品思考点，一句话概括，要抓人>" --folder dQPGYqjpJYZnRbNYCBxPjo448akx1Z5N --content-file /tmp/product_thinking_<标题>.md --format json
# 返回新建子文档的 nodeId

# 6c. 回读校验（必须）
dws doc read --node <新nodeId> --format json
# 确认内容完整写入
```

**关键规则**：
- 每次提取生成一个独立子文档
- **子文档标题必须是听记里最核心、最抓人的那个产品思考点**（比如"客户信任只有一次机会"、"企业付费看感知不看客观"），不要用日期或听记原名做标题
- 标题要有观点、有锋芒，让人一看就想点进去，像面试时能直接甩出来的那种
- 禁止直接 append 到父文档正文——父文档只作为目录容器
- 如果子文档创建失败，回退到本地文件输出并告知用户

## 输出要求

- 输出为 Markdown 文件（写入钉钉子文档）
- 保持带教的原始表述风格，不要过度美化
- "我的理解"部分要用实习生视角、朴素的语言
- 如果某个分类下没有内容，跳过而不是留空标题
- 如有不确定的内容标注 [?] 供用户确认

## 注意事项

- 不要编造原话，如果记录模糊就标注"大意是..."
- 区分事实（mentor 明确说了什么）和推测（你觉得 mentor 可能想表达什么）
- 一次谈话如果超长，可分段处理后合并
- **原话神圣不可侵犯**：只要判定为"亮眼原话"，必须一字不改（含语气词、停顿词）；宁可保留粗糙，也不做书面化润色
