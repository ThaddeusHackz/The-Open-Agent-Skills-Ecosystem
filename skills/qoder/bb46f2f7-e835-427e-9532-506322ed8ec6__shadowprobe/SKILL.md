# ShadowProbe：精排模型实验离线回查与分析

把这个 skill 当作"旁路双打分的回查与分析执行手册"。

## 你的角色与边界

**你做**：
1. 按用户输入准备回查 SQL（改 3 处配置）；
2. 指导或协助用户在生产环境执行；
3. 收到结果表后按固定框架逐层分析；
4. 产出语雀分析报告（本 skill 的核心产物）。

**你不做**：启动旁路工具、回收线上打分数据——这两步由用户完成。但如果用户环境里有可自动提交生产任务/执行 SQL 的工具，你要主动用起来（见"输入收集"第 5 项）。

## 输入收集（缺哪个反问哪个，不要自己编）

开工前必须拿到 5 项：

| # | 项 | 说明 |
|---|---|---|
| 1 | 实验改动一句话 | 改了什么（样本/结构/特征/loss/超参）+ 假设 |
| 2 | 主分析分数 | 默认 `score_click`；可换成 dual 日志里成对出现的其他单值分数 |
| 3 | dual 表名 + 分区 | **表名可能随实验变化**（字段保持一致即可），必须向用户问清 |
| 4 | 数据日期 | 跑哪个分区（ds/dt） |
| 5 | 环境能力探测 | 问用户："当前环境是否支持自动提交生产任务 / 执行 SQL 查询？" |

第 5 项的处理：
- **支持** → 检索当前环境可用的 skill / 工具（如 alps 相关 skill、ODPS 客户端、数据开发平台 CLI），用它们自动提交 SQL 并拉取结果表；
- **不支持** → 走人工流程：把 SQL 文件交给用户自己提，跑完让他把结果表贴回来。

## 执行步骤

### Step 1：收集输入
按上表逐项确认，任何一项缺失都先反问，不要假设。

### Step 2：准备回查 SQL
复制 `assets/shadowprobe.sql` 为新文件，替换 3 处配置：
1. **日期**：全局把 `20260909` 换成数据日期；
2. **dual 表名**：把 S0 中的 `aprecalgov2.home_df_rank_online_gauc_cal_day` 换成用户的 dual 表；
3. **主分数**：若不是 score_click，改 S0 中标记 `[MAIN_SCORE]` 的两处列名（下游全部走别名，不用动）。

### Step 3：提交执行
- **提醒用户：建议提交到生产环境跑**（s_dd 是全量大表，生产跑比本地/调试环境快得多）；
- 环境支持自动提交 → 用可用工具提交并跟进任务状态；
- 不支持 → 把 SQL 文件给用户，让他自己提交；跑完让他把结果表贴回来：
  `SELECT * FROM aprecalgov2.shiyan_reqfilter_probe_result WHERE ds='<数据日期>';`

### Step 4：收结果、过闸门
先做闸门检查（见下"第 0 道"），不通过先查数据问题，不做分析。

### Step 5：按框架逐层分析
见下面"分析框架与判读规则"。

### Step 6：生成报告并询问是否发布
1. **先本地生成**：按"报告规范"把报告全文写成 markdown 文件（保存到当前工作目录，如 `./shadowprobe_report_<YYYYMMDD>.md`），并把全文展示给用户；
2. **再询问发布**：问用户"是否需要发布到语雀？";
3. **需要发布** → 请用户提供他的知识库地址（namespace，形如 `xxx/yyy`），然后：
   ```bash
   yuque create doc --namespace <用户提供的namespace> --title "【<YYYYMMDD>】<实验名>·离线回查数据与解读（ShadowProbe）" --body-file <md文件> --json
   ```
   **不要默认写死任何知识库地址**——不同用户的发布目标不同，必须由他提供；
4. **不需要发布** → 保留本地 md 文件即可。

## 分析框架与判读规则

### 第 0 道：闸门（数��可信吗）
- `p0_joinchk`：`join_rate ≈ 1`、`score_match_rate ≈ 1`、`label_match_rate ≈ 1`、`slide_null_rate ≈ 0`、`dup_indicator ≈ 1`；
- `p0_headline` 与 `h1_user_type_gauc` 的 all_gauc 自洽（基线 GAUC 对得上已知值）。
- **闸门不过：停止分析，先修数据。**

### 第 1 问：增益是什么构成的（三层诊断）
比较三层指标（pooled AUC 跨用户 / user-day GAUC / trace GAUC 请求内）：

| 形态 | 结论 |
|---|---|
| 三层同涨、trace 涨最多 | 模型在学 item 好坏，最健康 |
| pooled / user-day 涨、trace 平 | 增强的是"认人/认场景"，同屏没变化 |
| trace 大涨、pooled 崩、req_auc 倒挂 | 同屏能力增强，但主动放弃了跨请求/跨用户区分（多见于激进样本策略） |
| user-day 涨、trace 不涨、pooled 异常 | 疑似评估口径产物，触发定制检查（位置偏差/泄漏排查） |
| 请求识别 req_auc：实验 < 0.5 | 倒挂 = 放弃了请求间区分 |
| 请求识别 req_auc：实验 > 基线 | 保留或增强了请求级识别 |

### 第 2 问：增益在哪里（定位）
按请求长度 / 首刷 / 充分曝光（expo≥90）/ 位次带 / 位次带×充分曝光拆 trace 级结果：
- 增益落在哪种请求（短/长）、哪个位置（首行/深位）——**首行是主战场**，要特别标注首行有没有增益；
- **充分曝光后翻正** = 增益真实存在，只是被低曝光噪声标签稀释；
- 逐请求胜负（win/tie/loss）与分歧对是**两条独立证据链**，结论一致才采信。

### 第 3 问：分数本身上线会不会出事（分数体检）

| 现象 | 结论 |
|---|---|
| 底部膨胀倍数 ≫ 顶部（如底 12x、顶 1.8x） | 分布被重塑，部署高危 |
| log 空间分数范围（p10→p90）大幅收缩 | 融合公式里发言权被腰斩，部署高危 |
| PCOC 大幅偏离基线 | 校准漂移，需校准后才能上 |
| 分人群均分被拉平（各人群分数趋同） | 失去用户分层，人群级校准难 |
| 分布形状保持、仅整体平移 | 尺度安全 |

### 第 4 问：谁受益、谁受损（人群账本）
user-day / trace 分人群看增益分布；受损人群要能归因到机制（训练覆盖缺失 / 校准漂移 / 构成变化），判断上线前是否需要单独处理。

## 报告规范（核心产物）

以"数据陈列 + 数据解读"为风格，以已有的 0903 报告为深度基准：

- **结构**：评估集构成 → 数据自校验 → 三层构成 → 请求内细化 → 分数体检 → 结构摆放 → 人群账本 → 总结；
- **所有数据入表**，表格为主、文字为辅，文字里不夹数字；
- **概念先给后用**：三层分解、可评估请求数（"有正有负才能比"）等首次出现先解释，后文直接用；
- **每大章节末尾有"本章小结"**（一两句，纯数据性）；
- **不做实验好坏评判、不给上线建议**；结尾只给高层次文字总结（这个改动改变了模型的什么能力、边界在哪）；
- 首行/首刷是场景主战场，相关结论必须单独点出；
- 小微 trace 会让 top2 重合、pos_agree 类指标机械偏高，报告里必须带局限说明；
- 标题格式：`【YYYYMMDD】<实验名>·离线回查数据与解读（ShadowProbe）`。

## 已知坑（写死，不要再踩）

- `PERCENTILE` 在部分环境返回全 0 → 一律用 `percentile_approx`；
- `CREATE TABLE IF NOT EXISTS` 不会更新老表 schema → 底座表用独立命名 `shiyan_shadow_*`，避免与历史表冲突；
- 自动 mapjoin 会把大表广播导致 mapper OOM → SQL 头部已内置 `set odps.sql.mapjoin.memory.max=0;` + 各阶段 4G 内存，不要删；
- `brush_index` / `brush_card_index` 是 0 基（首刷=0、首行=0/1 两坑）；
- item_attributes 取分：`KEYVALUE(item_attributes, '\001', '\002', '<字段名>')`；
- 双打分与线上样本表 join 键：`trace_id + content_id + user_id`。

## 进化机制

新回查角度以"指标卡"形式追加：名称 / 输入（表+字段）/ SQL / 结果怎么读 / 触发什么结论。追加到 `assets/` 并在本文件"分析框架"对应问题下登记判读规则。框架（闸门 + 四问）本身保持稳定，只增不减。
