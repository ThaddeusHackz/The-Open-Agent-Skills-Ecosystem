# HR 简历筛选

## 快速开始

当用户提供了岗位职责、任职要求以及保存 PDF 简历的本地路径后，按以下流程执行：

1. 读取所有 PDF 简历并提取文本
2. 结合岗位 JD 对每份简历进行多维度打分
3. 生成每位候选人的雷达图与综合评价
4. 输出一份按综合得分倒序排列的交互式 HTML 报告

## 输入要求

开始评估前，确认用户已提供：

- **岗位职责和任职要求**（可直接粘贴文本，或读取 JD 文件）
- **PDF 简历所在本地路径**（文件夹路径，支持批量处理）

如果用户未明确，主动询问。

## 评估维度

对每份简历从以下维度打分（0-10 分，可保留 1 位小数）：

1. **硬性基础匹配度**：学历、工作年限、专业、地点、职级等硬性条件
2. **岗位职责匹配度**：过往职责与目标岗位核心职责的匹配程度
3. **工作业绩匹配度**：可量化业绩、项目成果与岗位目标的契合度
4. **专业技能匹配度**：技术栈、工具、证书、行业知识与岗位要求的匹配程度
5. **稳定性与潜力**：跳槽频率、成长轨迹、学习新技能的意愿与能力

可根据具体岗位增加或调整维度，但需在报告中说明。

## 综合评价

对每位候选人输出：

- **综合得分**（0-10，精确到 0.1）
- **打分理由**（一小段，说明得分依据）
- **突出亮点**（分条目列出：工作业绩、新方法与新技能、工作态度等）
- **主要不足**（分条目列出：经验短板、技能缺口、稳定性风险等）

## 输出格式

最终输出为单个 HTML 文件，包含：

- 候选人列表，按综合得分从高到低排列
- 每位候选人的雷达图（使用 Chart.js CDN）
- 综合得分、打分理由、亮点与不足
- 支持点击展开/收起详情的基础交互
- 顶部汇总标签：强烈推荐、推荐面试、不推荐人数

参考 HTML 结构见 [reference.md](reference.md)。

## 执行方式

### 由 Agent 在会话中逐步执行

用户可按下列步骤由 Agent 在对话中完成：

1. 使用 `pdf` skill 或 Python 库（如 pdfplumber / PyPDF2）提取 PDF 文本
2. 将岗位 JD 与简历文本作为上下文，调用 LLM 进行评估
3. 将评分结果整理为 JSON 结构
4. 填充 HTML 模板并保存到输出目录
5. 向用户提供 HTML 文件路径

## 回退与容错机制

为避免某一环节失败导致整个任务中断，脚本内置了多层回退：

- **PDF 提取回退**：依次尝试 pdfplumber → PyPDF2 → pdfminer.six，任一成功即可继续。
- **单份简历失败不影响整体**：提取或评估某份简历失败时，该简历以“评估异常”状态出现在报告底部，其余简历正常打分。
- **LLM 调用重试**：网络或 API 偶发错误时自动重试 3 次，指数退避。
- **结果缓存与断点续跑**：已生成的 JSON 结果可复用，避免重复调用 LLM；PDF 文本也支持缓存。
- **重复文件自动去重**：同名简历仅处理一次，避免重复计分。

## 边界情况处理

- **扫描件 / 图片 PDF**：若提取文本过少（<30 字符），脚本会标记“提取到的文本过少”，并在报告中显示“评估异常”。建议用户先使用 OCR 工具转换为可搜索 PDF。
- **简历中关键信息缺失**：对应维度应给出较低分数，并在 reason 中说明“未提及 XX 经历/技能”。
- **JD 为空或极短**：脚本会正常读取，但建议用户补充完整岗位描述，否则评分可能失真。
- **简历文件名相同**：按文件名小写去重，同名文件仅保留第一份。
- **无 PDF 文件**：脚本直接报错并提示检查路径。

## 注意事项

- 严格基于简历中实际出现的信息打分，不臆测未提及的能力。
- 若简历扫描不清或提取失败，在报告中标注“文本识别受限”或“评估异常”。
- 综合得分不是各维度简单平均，应根据岗位优先级加权。
- 保留原始评分数据，便于用户复核。
- 评分结果仅供参考，最终录用决策应结合面试与背调。

## 常见问题（FAQ）

**Q1：安装依赖时 pdfplumber 报错怎么办？**
A：pdfplumber 依赖 pdfminer.six，通常需要预装 `libxml2`/`libxslt`（Linux）或 Xcode Command Line Tools（macOS）。如果仍然失败，可只安装 `PyPDF2` 和 `pdfminer.six`，脚本会自动回退。

**Q2：为什么有些简历显示“评估异常”？**
A：常见原因包括：PDF 是图片扫描件、文件已损坏、文件被加密、提取到的文本过少。可尝试用 OCR 软件预处理后再运行。

**Q3：评分结果看起来不够准，怎么优化？**
A：在 `job_description.txt` 中尽量写明岗位的硬性门槛和优先级，例如“必须 5 年以上 Java 经验”“必须有团队管理经验”。JD 越具体，评分越贴合需求。

**Q4：可以支持 Word / Excel / 图片格式简历吗？**
A：当前版本专注于 PDF。如需处理其他格式，建议先用 pandoc、python-docx、 mammoth 等工具转换为文本或 PDF 后再使用本脚本。

**Q5：为什么综合得分不是五个维度的平均分？**
A：综合得分由 LLM 根据岗位优先级加权得出，例如技术岗可能更看重“专业技能匹配度”和“工作业绩匹配度”。如需强制平均分，可修改 `screen.py` 中的 SYSTEM_PROMPT。

## 避坑指南

- **不要给 AI 传递过长的 JD**：简历文本 + JD 总长度建议控制在 12k-14k 字符以内，过长的上下文会稀释关键信息并增加费用。
- **不要把所有简历一次性塞给 LLM**：单份简历独立调用，既便于定位异常，也更容易并行和重试。
- **不要忽略“文本识别受限”标记**：这类简历很可能是扫描件，直接按低分处理会漏掉优秀候选人。
- **不要完全依赖综合得分**：LLM 对量化数字敏感，但对行业背景、软技能判断有限，建议把报告作为初筛参考。
