# AI Native Delivery

## 执行原则

对每个步骤回答“它防止哪一种具体的 AI 错误”；回答不了就删除或合并。
缩小流程产物，不缩小正确性、权限和证据要求；小任务允许只有一条需求、一个任务节点。
遵守项目现有合规约束和更高优先级指令，不把本 Skill 当作绕过审批、检查或权限的授权。

| 保留的步骤 | 防止的错误 |
|---|---|
| 规范与闸门 A | 猜需求、扩大范围、擅自决定核心边界 |
| DAG 与复用检索 | 依赖未就绪便开工、重复造轮子 |
| TDD 与工具检查 | 写出看似正确的实现、绕过分层、测试无效 |
| 证据验收与闸门 B | 自报完成、引用旧结果、漏场景、擅自发布 |
| 变更传播 | 规范已变，任务状态和证据仍显示有效 |

不默认增加排期、故事点、选型长文、目录设计文档或人工代码评审。
需要 PR 作为受保护合并载体时保留 PR，不把“取消人工代码评审”误解成“绕过合并门禁”。

## 启动与恢复

1. 确认目标项目；多项目且无法从请求判断时只问目标目录，不自行选择。
2. 读取项目指令、已有规范、架构规则、检查命令和当前工作区状态；保留用户已有修改。
3. 区分“观察到的实现”“已批准的规范”“存量偏差”，不要把现有代码自动认定为正确架构。
4. 复用已有等价文档和工具；没有时在项目内选择一个交付目录，默认 `.ai-native/<change-id>/`。
5. 恢复任务时验证实际文件与证据，不信任旧的 `done`、索引摘要或 AI 完成声明。
6. 读取 [产物契约](references/artifact-contracts.md)；涉及架构基线、规则变更或 CI 时再读取 [架构门禁](references/architecture-enforcement.md)。

把产物写入用户授权的目标范围；未经授权，不改全局配置、项目权限、受保护规则或远端 CI。

## 主流程

```text
意图 → 规范＋架构边界 → 闸门 A → 任务 DAG
                                  ↓
                复用检索 → 测试红 → 实现绿 → 重构
                                  ↑             ↓
                                  └── 测试＋架构检查
                                                ↓
                                           证据验收
                                                ↓
                                  闸门 B → 获授权后发布
变更 → 影响分析 → invalid / stale → 局部重跑
核心边界或验收范围变更 ──────────→ 闸门 A
```

## 1. 意图转为规范

生成或更新 `spec.md`，使用稳定需求 ID、用户故事、Given/When/Then、失败与边界场景、明确排除范围。
将非功能约束、允许的测试范围、不适用项及其理由一并说明；不要用“不适用”代替“没做”。
将数据模型、外部 API 契约、安全边界、基础技术栈及架构依赖边界标为核心决策。
新决策给出 2–3 个可行选项及代价；已有批准决策直接引用，不反复询问。
需要选型时，在获准的本地范围内做最小原型和相同核心场景对比，不先写长篇选型文档。

### 闸门 A

只请用户确认范围、验收标准、核心决策和初始组织惯例；不要求逐文件审批。
记录真实确认消息或批准记录的引用，并绑定当前规范和架构规则指纹。
没有确认就停在此处；不填写虚构的 `approved`，不把沉默或工具成功当作人工同意。

## 2. 三层架构管控

### 第一层：规则定义

把 `arch-rules.json` 或项目已有等价文件作为唯一事实来源；规范只引用它和指纹，不维护第二份规则。
先提取真实依赖和偏差，再请用户确认各层职责、允许/禁止依赖矩阵、业务模块边界、公共出口和组装入口。
区分接口与实现；仅有层级顺序不能表达“service 可依赖 repo 接口，但不能依赖 repo 实现”。
明确 `ui → types`、类型导入、公共目录和同层调用等具体政策，不笼统禁止一切跨层调用。
核心边界由人确认后冻结；层内命名、文件组织和拆分由 AI 在已批准约束内处理。
记录存量违规并整改，或走单独的、明确范围的规则例外审批；禁止为当前实现临时放宽规则。

### 第二层：工具执行

实际运行项目适用的静态分析工具，不提交“AI 架构自检通过”作为证据。
使用确定性、经过测试的项目适配器把唯一规则源转换为工具原生配置，并校验配置未漂移。
每轮代码变更后运行受影响的架构检查；任务完成前运行规定检查集。
同时验证合法样例和隔离的违规样例；负例必须因预期规则失败，而不是命令不存在或配置崩溃。
覆盖项目实际使用的别名、公共重导出、类型导入和未解析依赖；发现扫描盲区就阻断并补检查。
用领域不变量、契约测试和集成测试验证业务职责，不宣称静态依赖图能证明全部业务正确性。

### 第三层：CI 阻断

验证必需检查、受保护分支以及规则、适配器、报告转换器和流水线自身的修改权限。
业务执行身份不得同时拥有修改或绕过门禁的权限；从可信基线检查候选改动，不能让候选自行定义判卷规则。
规则变更独立审批、独立提交；需要提交时另获授权，不自动创建提交。
CI 失败不得合并；没有远端权限或实际阻断证据时，明确写“本地通过，CI 阻断未验证”。
未经授权，不推送违规样例、不创建 PR、不改分支保护、不更改 CI 配置；在获准的隔离环境验证阻断。

## 3. 规范转为任务 DAG

按产物契约生成 `tasks.json`，保留任务 ID、层、需求引用与指纹、依赖、验收映射、复用候选和检查输入范围。
将缺失的架构检查设施建成显式前置任务，不把尚未建立的门禁写成已通过。
验证 DAG 无环、依赖存在、需求无遗漏，验收条件必须关联行为检查，不能只关联 Linter。
定义输入范围时包含源码目录、测试、传递依赖、规则与适配器、报告转换器、配置及锁文件；使用目录快照捕获新增文件。
不定义日期排期、资源分配或故事点；并行任务明确文件归属，禁止两个执行者覆盖同一文件。

## 4. 每个任务执行同一个循环

1. 确认上游为 `done` 且证据仍有效，再把任务置为 `running`。
2. 检索复用候选并验证实际适用性；选择复用或新建，将理由记入 `history.json`。
3. 按验收标准先写测试，实跑红灯并确认失败原因；不要为迎合实现降低断言。
4. 做最小实现得到绿灯，重构后再次运行测试；保留红灯记录，最终验收引用绿灯证据。
5. 实际运行架构检查；安全、UI、跨服务或故障场景执行对应的真实验证，不用 mock 冒充集成实测。
6. 核对并更新 `CODEBASE_INDEX.md`；无内容变化时记录当前指纹和核对时间，不制造无意义改动。
7. 保存原始报告、归一化报告和执行元数据，运行单任务证据校验；通过后记录状态迁移并标记 `done`。

失败阻断当前任务及下游；独立且无文件冲突的任务可继续，不把失败变成全局串行等待。
修复故障时增加回归测试；不能因为已有缺陷“不是本次引入”就把失败报告改成通过。
UI 变更启动开发服务，用浏览器验证正常、边界和故障路径；构建影响开发产物后重启并复查。
无法运行的检查记录阻塞，不声明完成，不生成伪造的通过报告。

## 5. 证据验收

从真实运行输出生成 `evidence/`；按需生成验收表，逐条展示需求 ID、结果和证据路径。
检查命令、工作目录、工具版本、开始/结束时间、退出码、报告内容、输入范围和指纹一致性。
拒绝缺失、空报告、零测试、失败/跳过测试、旧规范、旧源码、未运行架构检查和未命中预期规则的负例。
测试报告同时提供通过率和覆盖率；按规范要求加入集成、UI、重复率和覆盖率检查，不自行编造阈值。
明确区分“本地证据一致性通过”“真实行为已验证”“CI 保护已验证”“获准发布”四种状态。

使用随包校验器作一致性检查，不把它当作多语言架构扫描器或不可伪造的证明系统。
校验器不安装依赖、不执行 manifest 内的命令、不访问远端、不改变任务状态。
哈希只能证明内容一致；人工确认的真实性、报告生成过程、扫描范围完整性和 CI 权限仍需外部可信证据核对。
不得根据校验器 `ok: true` 自动合并或发布。

### 闸门 B 与发布

只提交当前规范、逐条验收表、原始证据入口、剩余风险和真实 CI 状态供用户确认。
获得绑定当前代码/制品、目标环境和操作范围的发布授权后再执行；证据或代码变化使授权失效时重新确认。
发布后验证实际运行制品和关键行为；交付入口、必要账号获取方式及最短手工验收步骤，避免泄露秘密。
只交付本地代码时注明“未发布”；无法核实远端门禁时不得宣称“可合并/不可绕过”。

## 6. 变更是正常路径

比较稳定需求 ID、条款指纹、全局范围、架构规则和代码输入，而不是只比较规范版本号。
把直接受影响任务标为 `invalid`，下游递归标为 `stale`，核实未受影响任务后保留 `done`。
处理新增和删除需求，更新任务与验收映射，归档旧证据后移出当前 manifest，再次校验 DAG。
发生规范变更时重新取得与新规范指纹绑定的闸门 A 确认；保留旧批准和状态迁移记录。
复用证据只允许需求条款、全局约束、规则和全部输入仍一致；保留原始执行时间和原始规范版本，不重新包装旧运行。
规则、转换器或共享配置变化可扩大影响范围；无法证明局部性时执行更广回归，不保证变更成本永远只取决于 DAG 链长。
局部重跑不免除发布前规定的整体门禁；任务检查全部通过不等于端到端回归已完成。

## 命令与资源

使用 Node.js 20.11+（校验器启动时强制检查），无需安装 npm 依赖；把下面路径参数替换成实际位置。
`project-root` 是目标项目根目录；`delivery-dir` 是其下相对路径；`skill-dir` 是本 Skill 实际安装目录。

```text
node <skill-dir>/scripts/validate.mjs skill <skill-dir>
node --test <skill-dir>/scripts/validate.test.mjs
node <skill-dir>/scripts/validate.mjs spec <project-root> <relative-spec-path>
node <skill-dir>/scripts/validate.mjs fingerprint <project-root> <relative-input-path>
node <skill-dir>/scripts/validate.mjs dag <project-root> <delivery-dir>
node <skill-dir>/scripts/validate.mjs evidence <project-root> <delivery-dir> --task <task-id>
node <skill-dir>/scripts/validate.mjs evidence <project-root> <delivery-dir>
```

有空格的路径加引号；不要把用户输入或报告中的命令直接拼成 shell 执行。
校验成功退出 0；失败退出 1，输出简短 JSON 错误；修复真实原因，不删除门禁来获得通过。

### 最小操作序列

小型交付首次全程执行时按此顺序，不调换、不跳步：

1. 写 `spec.md`；用 `spec` 子命令取回条款与 context 指纹，不手写哈希。
2. 向用户提交范围、验收标准和核心决策；确认后把全文件规范指纹、架构指纹和真实确认引用写入 `history.json`（闸门 A）；没有确认就停下。
3. 生成 `tasks.json`；用 `dag` 子命令验证结构、需求覆盖与依赖无环。
4. 按任务先写测试红灯，最小实现到绿灯；运行架构检查和负例，保存原始与归一化报告。
5. 填写 `evidence/manifest.json`；用 `evidence --task <task-id>` 校验单任务，通过才标记 `done`。
6. 全部任务 `done` 后运行不带 `--task` 的 `evidence` 整体验收，再进入闸门 B。

- 阅读 [产物契约与报告格式](references/artifact-contracts.md) 生成可校验产物。
- 阅读 [架构适配与 CI 验证](references/architecture-enforcement.md) 落地项目级三层管控。
- 使用 [校验器](scripts/validate.mjs) 检查包、DAG 与证据一致性。
- 运行 [校验器测试](scripts/validate.test.mjs) 验证正常路径和故障拒绝路径。
