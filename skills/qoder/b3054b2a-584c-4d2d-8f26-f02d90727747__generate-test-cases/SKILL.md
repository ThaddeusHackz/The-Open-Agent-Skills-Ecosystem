# 生成测试用例

## 三层规则体系

本 skill 基于三层规则生成测试用例，执行时自动读取并合并：

| 层级 | 文件 | 作用 | 更新频率 |
|------|------|------|---------|
| 全局 | [rules/global.md](rules/global.md) | 跨项目通用规则（权限、边界、格式） | 几乎不改 |
| 项目 | [rules/project.md](rules/project.md) | 当前项目特有规则（功能、标签、结构） | 项目周期内偶尔调整 |
| 迭代 | [rules/iteration.md](rules/iteration.md) | 本次迭代重点（范围、变更、关注点） | 每次迭代更新 |

## 执行流程

### Step 1：前置操作

```bash
cd c:\TestTools\code\busyming-mcp-service
git pull --rebase
```

确保基于最新代码和需求文档生成用例。

### Step 2：检测版本并确认

检查 `product-project/` 目录下是否存在多个版本目录（如 v20260624-0.1、v20260628-0.2 等）：

```bash
ls product-project/ | Where-Object { $_ -match '^v\d+' }
```

- **如果只有一个版本目录**：自动使用该版本，无需询问
- **如果存在多个版本目录**：必须询问用户要对照哪个版本生成测试用例

询问示例：
> 检测到以下版本目录：
> 1. v20260624-0.1
> 2. v20260628-0.2
>
> 请问要对照哪个版本生成测试用例？

用户确认后，使用指定版本目录下的 spec.md、requirements.md、tasks.md 和 demo 作为输入来源。

### Step 3：读取三层规则

依次读取 rules/global.md、rules/project.md、rules/iteration.md，合并为完整的生成规则集。

### Step 4：读取需求文档

根据迭代规则中指定的路径，读取目标模块的：
1. `spec.md` — 功能规格
2. `checklists/requirements.md` — 需求清单
3. `tasks.md` — 任务分解
4. Demo 目录 — 交互参考

先完整读取上述文件，理解功能需求后再生成用例。

### Step 5：生成测试用例

按照三层规则合并后的要求，生成完整测试用例：
- 正向功能 + 边界条件 + 异常处理 + 权限校验 + 无障碍
- 同时输出 AI 执行版和人工阅读版

### Step 6：输出与检查

1. 写入 `test-project/ai-version/{编号}-{模块名}.md`
2. 写入 `test-project/manual-version/{编号}-{模块名}.md`
3. 更新 `test-project/README.md` 统计信息
4. 确认两版本内容同步、编号递增且无重复（允许因历史删除导致的空洞）

## 规则优先级

当规则冲突时，优先级为：迭代 > 项目 > 全局

## 使用方式

用户只需说：
- "帮我生成 XXX 模块的测试用例"
- "根据最新 spec 生成测试用例"
- "/generate-test-cases"

无需手动指定规则，自动组合三层规则执行。

## 输出规范

### 双版本同步输出

每次生成必须同时产出两个版本，存放路径：

| 版本 | 路径 | 用途 |
|------|------|------|
| AI 执行版 | `test-project/ai-version/{编号}-{模块名}.md` | AI 自动化测试执行依据 |
| 人工阅读版 | `test-project/manual-version/{编号}-{模块名}.md` | 人工查看和评审 |

两个版本必须严格同步，内容一一对应，禁止仅生成其中一个。

### AI 执行版格式

```markdown
# {模块名} 测试用例（AI 执行版）

## 一、{功能分组名}

### TC-{分组缩写}-001: {用例标题}

- **优先级**：P0/P1/P2
- **前置条件**：
  - 条件1
  - 条件2
- **测试步骤**：
  1. 步骤1
  2. 步骤2
- **预期结果/断言**：
  - 断言1
  - 断言2
```

AI 版需包含以下测试层次：
- 后端 API 测试（接口请求/响应验证）
- 前端组件单元测试（组件渲染/交互）
- E2E 端到端测试（完整用户流程）
- 无障碍测试（ARIA 标签、键盘导航）
- 边界条件与异常测试

### 人工阅读版格式

```markdown
# {模块名} 测试用例

## 一、{功能分组名}

| 编号 | 测试场景 | 操作步骤 | 预期结果 |
|------|---------|---------|---------|
| 1 | 场景描述 | 用户做什么 | 看到什么 |
```

人工版要求：
- 全部使用中文
- 从用户视角描述（用户做什么 → 看到什么）
- 不包含代码、API 路径、CSS 选择器等技术细节
- 用表格形式，一目了然

## 覆盖范围要求

每个模块的测试用例必须覆盖以下维度：

### 1. 正向功能测试
- 核心业务流程的正常操作路径
- 各功能模块的标准使用场景

### 2. 边界条件测试
- 字段为空/缺失时的兜底展示
- 超长文本的截断处理
- 异常数量（0个、大量数据）
- 网络离线提示

### 3. 异常处理测试
- 加载失败与重试机制
- 接口超时处理
- 数据格式异常的容错

### 4. 权限校验测试（重要）

权限校验用例的详细规则见 `rules/global.md` 权限校验章节。如果页面功能需要登录，必须包含权限测试用例组（未登录访问、登录方式验证、登录态过期、无权限访问等场景）。

### 5. 兼容性测试（按需）
- 不同浏览器表现
- 剪贴板 API 兼容性

## 编号规范

### 模块编号

001-009 为页面功能，010 为性能测试

### 编号规则

- **首次生成**：为某模块首次生成测试用例时，编号从 1 开始连续递增
- **迭代更新**：迭代过程中因任务删除导致用例删除时，允许编号出现空洞，不重排（避免与已有 Bug 记录中的编号引用冲突）
- **新增用例**：编号追加在该模块已有用例末尾（取当前最大编号 +1）

### 用例 ID 格式

`TC-{分组缩写}-{三位数字}`（如 TC-API-001、TC-E2E-003）

## 性能测试

性能/并发测试独立为 `010-performance-test.md`，覆盖：
- 高频调用（同一用户短时间连续请求）
- 并发用户（多用户同时操作）
- AI 搜索并发（多用户同时流式搜索）
- 系统稳定性与降级
- AI 服务容错（异常返回、超时、中断）

## 生成后检查

生成完成后必须：
1. 确认两个版本文件都已创建
2. 确认编号递增且无重复（允许因历史删除导致的空洞）
3. 更新 `test-project/README.md` 中的用例总数统计
4. 更新 `test-project/ai-version/README.md` 和 `test-project/manual-version/README.md`

## 注意事项

- 如果是更新已有模块的用例，先读取现有文件，在末尾追加或修改对应部分
- 如果是新增模块，按编号规范创建新文件
- product-project 的 spec.md、plan.md、tasks.md、requirements.md 不要修改
- 每个页面模块如涉及登录功能，必须包含完整的权限校验用例组
- **临时脚本/文件清理**：执行过程中若生成了临时脚本或临时文件（如 `.tmp-*.json`、`.py` 辅助脚本等），任务完成后必须立即删除，不得留在项目目录中
- **优先级字段强制**：每个生成的测试用例必须包含 `- **优先级**：P0/P1/P2` 字段。缺失优先级字段的用例视为生成不完整，须补充后再输出。优先级判定标准：
  - P0：核心用户流程、权限校验、数据安全性（如登录、核心CRUD、数据隔离）
  - P1：常规功能验证、边界条件、异常处理（如搜索、分页、字段校验）
  - P2：辅助功能、UI细节、补充验证（如文案检查、无障碍、样式一致性）
- **前置条件分类标注**：前置条件中须标注类型，使用以下标识：
  - `[ENV]`：环境前置（如"[ENV] 服务已部署且可访问"）
  - `[DATA]`：数据前置（如"[DATA] 账号已申请API Key"）
  - `[OP]`：操作前置（如"[OP] 已完成登录流程"）
- **数据构造标注**：涉及数据依赖的用例（标注了 `[DATA]`）须在前置条件中用 `【数据构造】` 说明数据准备方式，用 `【数据验证】` 说明如何确认数据就绪。参考 global.md 第十六章的规范。
