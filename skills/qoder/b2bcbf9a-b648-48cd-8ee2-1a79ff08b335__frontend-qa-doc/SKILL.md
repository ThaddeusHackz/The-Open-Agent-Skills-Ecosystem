# 前端提测文档生成

## 概述

把当前需求分支的改动整理成一份测试可直接使用的《前端提测文档-<分支名>.md》：每个功能点包含页面入口、涉及接口、改动说明、影响范围和可勾选的验证要求，末尾附回归范围汇总。文档同时供人和测试 AI 阅读，字段名和结构必须保持稳定。

## 输入

- 必需：当前分支相对基线的 git 提交（由脚本采集）。
- 推荐：需求文档/验收标准、后端接口说明（如《后端提测文档-接口说明.md》）、UI 设计稿、测试环境与账号。
- 缺少资料时照常生成，但推断内容标注【推断，待确认】，并在交付说明中列出需要人工确认的点。

开始前只问一次必要信息，不要逐项盘问：

1. 需求文档/接口文档路径或链接（用户已提供则跳过）。
2. 是否需要包含未提交改动（默认不包含）。
3. 输出路径（默认仓库根目录 `前端提测文档-<当前分支名>.md`，分支名中的 `/` 替换为 `-`）。

需求文档读取方式：

- `.docx`：macOS 用 `textutil -convert txt -stdout <file>`；其他环境用
  `python3 -c "import zipfile,re,sys; d=zipfile.ZipFile(sys.argv[1]).read('word/document.xml').decode('utf8'); d=re.sub(r'</w:p>','\n',d); print(re.sub(r'<[^>]+>','',d))" <file>`。
- `.pdf`：用 Read 工具按页读取。
- 飞书/Confluence/Jira 链接：优先使用用户导出的本地文件；WebFetch 无法访问鉴权页面时，请用户导出或粘贴关键内容。
- 只提取与本次需求相关的页面、交互、字段、权限和验收标准，不要把需求文档全文搬进提测文档。

## 硬性约束

- 只分析当前分支。禁止 `git checkout`、`git switch`、`git stash`、`git reset`、`git commit`、`git push`。
- 需要查看基线版本代码时，用 `git show <base>:<path>` 只读读取，不得切分支。
- 当前处于 main/master/develop/release/hotfix、GJ-DEV/GJ-PRE/GJ-UAT/GJ-PROD 等保护分支时拒绝生成。
- 当前分支不是 `feature-` 开头时，先提醒用户确认分支是否正确；用户确认后才能继续。
- 只新增或修改提测文档；不改业务代码、配置和依赖。首次确认基线后，只有用户同意才写入 `.frontend-qa-doc.json`。
- 文档中不得写入真实账号密码、token、内网密钥，用 `{{测试账号}}` 等占位符。
- 目标文件已存在时先读取并询问：覆盖 / 另存为带时间戳的新文件。
- 改动范围必须限定在 `merge-base(当前分支, 基线)..HEAD`。若 merge-base 异常（分支从旧版本或其他 feature 分支切出、混入大量无关提交），先报告实际提交范围并请用户确认，再生成。

## 执行流程

### 第 1 步：采集分支与改动

```bash
bash <skill目录>/scripts/collect-changes.sh --root <仓库路径> [--base <基线>] [--include-uncommitted]
```

脚本只读执行，输出当前分支、基线、merge-base、基线候选表、提交列表、改动文件清单、目录/类型汇总、技术栈线索和工作区状态。

基线解析顺序：

1. `--base` 参数；
2. 仓库根目录 `.frontend-qa-doc.json` 的 `baseBranch`；
3. 自动探测：优先选择已完全包含于当前分支、且本分支领先提交数最少的祖先分支；没有祖先候选时，回退到 main/master/develop/dev/uat/pre/prod/release 等主干候选中领先提交最少的分支。当前分支尚无提交时取最近的相同祖先，并提示没有可提测提交；
4. 候选并列或无法判断时脚本退出码 6，向用户展示候选表并请其指定，再用 `--base` 重跑。

处理脚本异常：

- 退出码 3：当前在保护分支（含 GJ-DEV/GJ-PRE/GJ-UAT/GJ-PROD 等 GJ-* 分支），停止并提示切换。
- 退出码 4：无法确定基线，请用户指定。
- 退出码 6：候选并列，展示 ahead/behind 后让用户选择。
- 退出码 7：当前分支不是 `feature-` 开头。先向用户确认分支是否正确；确认无误后用 `--allow-non-feature` 重跑。
- 当前分支相对基线没有提交：提示先提交，或确认后用 `--include-uncommitted` 基于工作区改动生成，并在文档头部注明“含未提交改动”。
- 多仓库/微前端：对每个仓库分别执行，最终按子应用分节合并到同一份文档。

### 第 2 步：读取改动内容

- 先读路由、页面、API、公共组件等高价值文件，样式和静态资源可只看摘要。
- 按文件分批读取 diff，避免一次性输出过大：

```bash
git -C <repo> diff <merge-base>..HEAD -- <path>
git -C <repo> show <base>:<path>
```

- 重命名文件（`R100` 等）要同时检查旧路径的引用是否已全部更新；移入公共目录的组件必须纳入回归。
- 需求文档给出预期行为、验收标准和边界值；接口文档给出字段、枚举、错误码和生效规则。三者冲突时以需求文档为准，并在“待确认”中记录冲突。

### 第 3 步：把改动映射成功能点

按 [references/change-mapping.md](references/change-mapping.md) 执行：

- 识别技术栈（React / Vue2 / Vue3 / 小程序 / Taro / uni-app / H5 / Electron / 混合仓库）。
- 把改动文件定位到页面、路由、菜单入口和接口。
- 同一页面或同一需求的多文件改动合并为一个功能点；公共组件、工具函数、路由权限的改动单列，并列出受影响的页面。
- 标注改动类型：新增 / 修改 / 修复 / 契约变更 / 样式调整。
- 列出前端特有影响面：权限点、字典、导出、i18n、浏览器与端兼容。

### 第 4 步：写验证要求

按 [references/verification-guide.md](references/verification-guide.md) 执行，保持与后端示例一致的简洁 checklist 风格：

- 每个 `[ ]` 一行，包含可观察的操作与预期；前置条件内联为“前置：…”。
- 覆盖主流程、边界值、空态/加载态/错误态、权限，以及与本次改动相关的契约和兼容性。
- 禁止“功能正常”“显示正确”“无异常”等无法判定的描述。
- 只写本次改动带来的验证点，不把整个模块的通用用例搬进来。

### 第 5 步：生成文档

默认写入仓库根目录 `前端提测文档-<当前分支名>.md`（分支名中的 `/` 替换为 `-`），使用下方模板。提交范围、基线、日期必须与脚本输出一致。

```markdown
# 前端提测文档

- **项目/仓库**：`<repo>`
- **提测分支**：`<branch>`
- **基线分支**：`<base>`（merge-base `<sha>`）
- **提交范围**：`<sha>..<HEAD>`，共 `<n>` 个提交
- **提测日期**：`YYYY-MM-DD`
- **提测环境**：`<环境地址 / 待填>`
- **需求来源**：`<PRD 链接或文件路径 / 待填>`

## 一、提测内容

### 1. <模块>：<功能点>（新增 / 修改 / 修复 / 契约变更 / 样式调整）

- **页面与路由**：`/xxx`（菜单：XX管理 > XX页面）
- **涉及文件**：`src/pages/xxx/index.jsx`
- **涉及接口**：`POST /v1/xxx/list`（无接口调用写“无”）
- **改动说明**：新增时写功能预期；修改时写“原逻辑：…；改动后：…”
- **影响范围**：公共组件、关联页面、权限点、字典、导出、兼容性；无则写“仅本页面”
- **验证要求**：
  - [ ] 前置：…；操作…，预期…
  - [ ] ……

## 二、回归测试范围汇总

#### 1. <回归点>

- **回归页面**：`/xxx`（菜单入口）
- **回归原因**：…
- **回归级别**：P0 / P1 / P2
- **回归方式**：
  - [ ] ……

## 三、环境与测试准备

- **账号角色**：…
- **初始数据**：…
- **开关/配置**：…
- **Mock/依赖**：…

## 四、已知风险与待确认

- 【推断，待确认】…
- 不在本次范围：…
- 已知限制：…
```

可选附录：变更文件按目录汇总，仅在文件较少且有助于提测人自查时添加。

### 第 6 步：自检并交付

逐项检查：

- [ ] 每个改动页面/接口都归属到某个功能点，或明确写为“无用户可见影响”。
- [ ] 每条验证要求都有页面入口、操作和可判定的预期结果。
- [ ] 契约变更写清了“原逻辑/改动后”，并列出了旧数据、空值、导出等验证点。
- [ ] 公共组件、工具函数、权限与路由改动已进入回归汇总并给出受影响页面。
- [ ] 回归级别符合 P0/P1/P2 规则，核心流程和契约变更不得低于 P0。
- [ ] 文档头部信息与脚本输出完全一致，没有遗漏或混入其他分支的改动。
- [ ] 文件名符合 `前端提测文档-<当前分支名>.md`，分支名中的 `/` 已替换为 `-`。
- [ ] 除环境与账号占位外，没有遗留待办占位或空字段。

交付时说明：文档路径、功能点数量、回归点数量、哪些内容来自推断、哪些环境信息需要人工补充。不要自动提交文档，除非用户明确要求。

## 基线配置（可选）

首次确认基线后，可询问用户是否在仓库根目录写入 `.frontend-qa-doc.json`，避免重复询问：

```json
{
  "baseBranch": "origin/GJ-PROD"
}
```

用户不同意则不创建该文件，后续每次通过候选表确认。

## 资源

- `scripts/collect-changes.sh`：只读采集分支、提交范围、改动文件与技术栈线索。
- `references/change-mapping.md`：多技术栈下改动文件到页面、路由、接口、影响面的映射规则。
- `references/verification-guide.md`：验证要求写作规范、前端测试维度、回归级别判定。
