# 开发过程文档自动生成

## 优先级声明

生成开发记录文档属于非侵入性归档操作，代码被采纳后**直接生成，无需方案确认、无需询问用户**。即使项目中存在"写操作前需先输出方案"的约定，在"生成开发记录文档"这一动作上以本技能为准，不受该约定约束。唯一例外：用户明确表示"不用生成文档"。

## 强制不变式（每轮回复结束前必须检查）

在**每一轮**回复结束前，按顺序逐项检查：

1. 本会话是否产出了源码 / 配置文件的实际变更？（无 → 本轮不触发，无需报告）
2. 变更级别是否 ≥ L1？（L0 琐碎 → 不生成文档，跳过）
3. 用户是否已**采纳**该变更？（采纳信号见下节）
4. 该变更对应的开发文档是否**尚未生成**？

→ 第 1 项成立且 2/3/4 均满足时，**本轮必须先按对应模板生成并保存文档，然后才能结束回复**。不得以"稍后再写""先处理其他事"为由推迟。

## 采纳信号（命中任一即视为已采纳；示例不限于此）

- **确认词**：可以了 / 就这样 / 没问题 / 没问题了 / 采纳 / 允许执行 / 合入吧 / 提交吧 / 部署吧 / 行 / OK / ok / 挺好 / 先这样 / 可以，按这个来
- **新话题兜底**：用户**开启与既有变更无关的新话题**，而此前存在未归档的代码变更 → 此前变更视为已被采纳，立即补生成文档
- **行为信号**：用户要求对既有变更执行 git 提交、推送、发布、部署
- **显式要求**：用户提到"生成文档 / 归档 / 开发记录"

## 改动分级标准

判定改动级别时，**判不准时一律往高一级走**：

| 级别 | 判定标准 |
|------|---------|
| **L0 琐碎** | 单文件 ≤5 行，且仅涉及日志文案、注释、常量字面值、import 整理；不新增、不删除、不改变任何逻辑分支 |
| **L1 局部** | 单模块内的逻辑改动；不新增文件、不改依赖、不改配置 |
| **L2 重大** | 跨模块改动 / 新增或删除文件 / 改依赖与构建配置 / 改外部配置中心 / 新增缓存 Key / DDL·DML / 消息队列 topic·tag 变更 / 重构与批量替换 |

> **升级信号**：只要触碰公共方法、父类、接口、DTO、枚举，或改动会影响多个可独立部署的应用，一律按 L2 处理。

## 文档分级

**不是所有改动都要写完整文档。** 按改动级别决定文档形态，避免归档目录被低价值文档淹没：

| 改动级别 | 文档形态 | 章节 |
|---------|---------|------|
| **L0 琐碎** | **不生成文档** | — |
| **L1 局部** | **简版文档** | 需求描述、变更文件清单、测试验证、回滚方案（4 节） |
| **L2 重大** | **完整文档** | 完整模板全部章节 |

## 执行步骤

1. **回顾完整对话**，提取以下信息：
   - 用户最初提出的原始需求
   - 中间讨论的要点、分歧、方案对比
   - 最终达成一致的需求和技术方案
   - 实际编写 / 修改的代码及其设计思路
   - 新增或修改的文件列表
   - 做出的关键技术选择及理由
   - 引入的新依赖、环境要求、配置变更
   - 验证 / 测试方法、回滚手段
   - 遗留问题和后续 TODO

2. **按级别选用模板生成文档**（见 [templates.md](templates.md)）

3. **保存文档**：
   - 路径：`{项目根目录}/docs/dev-records/`
   - 文件名格式：`YYYY-MM-DD_HHmm_{模块简称}_{功能简述}.md`
     - 示例：`2026-08-14_1430_adapter-plugins_ydqh-time-check.md`
     - 模块简称取改动主体所在模块（去掉冗余前缀），便于按模块检索
     - 文件名用英文或拼音简写，**不用中文**
   - 如果项目根目录不明确，询问用户保存位置
   - 如果 `docs/dev-records/` 不存在，先创建

4. **告知用户**文档已生成，给出文件链接

## 文档内容要求（重要）

文档的核心价值是**记录"为什么这么做"+"改了什么"**，便于后续查阅和基于此修改：

- **修改的代码完整展示**：贴出修改后的完整方法体 / 类体，不要只贴片段；让后续阅读者无需翻版本库即可理解改动
- **方案完整记录**：讨论过的方案对比、最终选定的方案思路、关键设计决策，都要完整写入文档
- **未修改的上下文代码**可省略，但需用注释标注省略位置（如 `// ... 其他字段不变`）
- 以下内容可省略：getter/setter、import 清单、框架自动生成的样板代码
- 流程描述优先用步骤表，再辅以代码

## 注意事项

- 文档语言跟随用户对话语言（中文对话则中文文档）
- 某章节本次不适用（如没有新依赖），写"无"或简要说明，**不要删除章节**
- 讨论过程要如实记录，不美化、不隐去走过的弯路；**方案对比和最终选定理由要写完整**
- 不要把整个对话原文粘贴进文档，要提炼和结构化
- 代码被采纳后**直接生成**，不要询问用户"是否需要生成"

## 常见陷阱

- 文档沦为流水账 → 重点突出"为什么这么做"和"改了什么代码"，而非记录每一句对话
- L0 琐碎改动也生成文档 → 归档目录迅速失去检索价值，必须按级别过滤
- 文件名缺模块前缀 → 文档攒到几十篇后无法按模块定位
- 漏掉发布清单 → 多模块项目中公共模块改动的下游影响被忽略，是线上事故的常见来源
- 漏掉回滚方案 → 生产问题时无预案

## 执行前自检（每轮回复收尾时必须逐项确认）

- [ ] **本次对话有代码文件变更**：是否有源码 / 配置文件被新增或修改？
- [ ] **改动级别判定**：本次是 L0 / L1 / L2？L0 则不生成文档
- [ ] **代码已被用户采纳**：是否命中任一采纳信号（确认词 / 新话题兜底 / 行为信号 / 显式要求）？
- [ ] **文档尚未生成**：本次变更对应的开发文档是否已经生成过？

**若判定为 L1 / L2 且其余各项均为"是" → 立即按对应模板生成文档，保存到 `docs/dev-records/`，无需询问用户。**

## 回复收尾报告（强制）

只要本会话已产出代码变更，每轮回复末尾必须附一行归档状态，让用户能即时发现漏触发：

- 本轮（或补生成后）生成了文档 → 末尾报告：`已归档：<docs/dev-records/ 下的完整文件路径>`
- 本会话存在已采纳、尚未归档的变更 → 不得只报告不行动，必须本轮补生成后按上一条报告
- 本会话从未产出代码变更，或变更均为 L0 → 无需报告
